# EDF5 任务包联机：BVM 玩家原生函数的联机分支（2026-10-10，静态，H 除非另注）

## 现象

2026-10-10 两台机器联机打 EDF5 DLC2 包第 1 关（`EDF5_OLD_SCRIPT/DLC/DM002`，房间 `DLC = 5`、`MISSION_NO = 1`）。两边一直黑屏，38 秒后房主退出：

- 房主以约 20 Hz 给客人推送对象状态（`NETTYPE 0x03300`）；客人那边房主的远程副本一直在报 `WORLD target: remote copy … chooses its own target (it has none)`。DM002 的敌人（`e506_ha_biggrey_ll`）是在 CreatePlayer **之后**才生成的（字节码 pc 0x62D 起），所以脚本已经越过了 CreatePlayer，只是场上一个玩家都没有，敌人也就没有目标。
- 两边插件都没有记 `MISSION start`（AF 挂在玩家预加载上），Coop 也没有记 `MISSION CreatePlayers`。

原版 EDF6 离线、在线都不会运行 `EDF5_OLD_SCRIPT` 里的脚本：原版那 28 关 EDF5 时代的关卡用的是重写过的 `EDF6/RM015B2` 等（`MISSION.AC`）。所以 BVM 执行器的联机路径从来没有被原版走过。

## BVM 执行器

- `MissionScriptBVMImplement`：单步函数在 `EDF+10AB600`（跳转表 `10AC49C`，opcode 0..0x38）。opcode 0x2C..0x2F 是原生调用，立即数是原生编号，经 `[[proc+0xD8]]+0`（vtable `179D298` 的 slot 0）进入分派器 `EDF+20FF70`。
- DM002 的 `Main`：BeginLoading(0x0A) → Preload(0x0D)… → PreloadMap(0x0E) → **PreloadPlayerResource(0x10)** → WaitPreload(0x0C) → Online_WaitStart(0x2710) → EndLoading(0x0B) → … → **CreatePlayer(0x3E8)** → 敌人分队 / 敌人。和 AngelScript 的 `M001.AC` 是一一对应的顺序。

## 两个空的联机分支

联机判据和 AngelScript 那边一样：`[GS+0x38] != -1`（GS = `[EDF+20B2890]`），并且 `[[GS+0x20][slot]+0x10]` 的虚基对象 `+0x68 != 0`。

| 原生函数 | BVM 实现 | 联机时 | AngelScript 对应 |
|---|---|---|---|
| 0x10 PreloadPlayerResource | `225E30`，唯一调用点 `210AE0`（`lea rcx,[r14-0x30]`） | `225EA9 call 20C5B0` 传 `rdx = r8 = 0`（`vector<shared_ptr>::assign` 赋空区间），然后析构空 vector 并返回；`225FAC` 那个联机调用永远走不到 | `1B8CC0`：从会话对象（`[EDF+20B2AC0]-0x98` 的 `+0xD0`，调用 `vf+8`）取出玩家列表，逐个调用 `59DC90`（`1B8E98`）；离线分支是同样的 `59DE50(i)` 循环（`1B8F52`）。两个函数都不读参数 |
| 0x3E8 / 0x3E9 / 0x3EA CreatePlayer / _NoWeapon / _InitWeapon | `22B1C0(rcx = BVM 对象, rdx = wchar_t* 出生点名, r8d = 模式 0/1/2)`，调用点 `2142F2 / 21430E / 214332` 与跳板 `21D8C3 / E6 / F6` | `22B36C..22B399` 同样赋空区间，然后 `22B39F jmp 22BB94` 跳过整个创建循环 | `1BCC50(rcx = AS 绑定对象, rdx = const wstring*, r8d = 模式)` → `1D9520`：联机和离线**共用一个循环**，只有人数不同：离线 `GS+0x14FF4`，联机 `GS+0x14FF8`（`1D95F4`） |

第三个同样的空壳 `22C4D0` 只在 `.pdata` 里有记录，没有调用者，也没有被虚表引用。全映像里调用 `20C5B0` 的只有这 3 处。

AngelScript 的实现不能直接拿来给 CreatePlayer 用：AngelScript 原生函数的 rcx 是 AS 实现对象 `+0xF8` 处的绑定对象（注册函数 `1E31F0` 由 `1DD8BD` 以 `rdx = [rdi+0xF8]` 调用），它的 `+8` 是 AngelScript 任务对象，玩家表在 `+0x100`。BVM 对象的玩家表在 `+0x168`，两边各管各的。

## 修法（`src/edf5online.cpp`）

1. `210AE0` 的 `call 225E30` 改为调用 `1B8CC0`（经 `RedirectCall`，先核对原目标）。之后 AF 已有的 `1B8E98` / `1B8F52` 钩子照常触发 `MissionStart`。
2. `22B36C` 写入 17 字节：`mov rax, &Edf5BvmOnlinePlayers; call rax; mov r13d, eax; jmp short 22B3B0`。人数是会话人数 `GS+0x14FF8`，然后进入原有的创建循环。
   - 状态：离线路径也是从 `22B353 / 22B36A` 跳到 `22B3B0`。那时 `xmm0 = 0`（`22B333`），`r15 = 0`，`[rbp-0x58]` 是空 vector；循环用到的输入只有 `r13d`。
   - 调用约定：插入点的 rsp 是 16 字节对齐的（函数序言之后），被调函数可能写的 `[rsp+0..0x1F]` 是本函数的出参影子区，此时没有活数据（`22B38A` 读的 `[rsp+0x50]` 不在这个范围内）。
   - 单人创建 `22AB90` 创建对象的联机分支是完整的：`22AC2F` 调用 `591130(ecx = 序号, rdx = 矩阵, r8d = 模式)`，和 AngelScript 的 `1DC525`（`ecx = [记录+8]`，`r8d = [记录+0x54]`）一致。
   - **但它的第 5、6 个参数在联机时不对**（2026-10-10 审查发现，`d8254fe` 修复）。第 5 个是本机手柄号，循环从常量 `{0,1,2,3}`（`1765B00`，`rbp+0x150`）里取；第 6 个是分屏除数，就是循环人数 `r13d`（`22B60F`）。`22AB90` 在 `22ACF6` 读手柄号：小于 0 时跳到 `22AFB1`，既不绑定输入也不建视口；否则先 `54ED40` 绑定这个手柄，再按 `[rbp+0x108]`（除数）切分视口宽度（`22AD43..22AD5E`），然后 `1198C40` 建视口。原样跑的话，每台机器都会按会话人数分屏，而且所有机器的 0 号玩家都绑定本机手柄。
   - AngelScript 的做法（`1D9520`）：先取会话用户列表（与 `1B8CC0` 同一个会话对象，`734670` 拷贝 `vf+8` 的结果），对每个用户调用 `12AC420`，即 `(用户+0x10 >> 1) & 1` 的远端位（`1D98B1`）。手柄号：远端填 -1，本机填本机计数（`1D9A64..1D9A74`）；本机计数只在创建成功、且玩家 `+0x128` 第 0 位为 0 时递增（`1D9B50..1D9B5F`）。除数填本机人数 `GS+0x14FF4`（`1D9A77`）。
   - 修法：`22B36C` 处的人数函数进入循环前读一次会话用户的远端位，按序号记下；参与者准入门包住的正是 `22B626 → 22AB90` 这个调用（`mission_participant_gate.cpp` 的 `UpperHook`），在那里按 AngelScript 的规则改写第 5、6 个参数，创建后回报玩家对象，供本机计数递增；循环最后一个序号处理完就解除。准入门在 `MissionStart` 的 `ResetSupportDispatch` 里安装，早于创建。准入门没装上、或者会话用户列表读不到时，人数函数返回 0，一个玩家都不创建，并记日志：宁可黑屏，也不能绑错手柄、分屏。
   - **第 i 号玩家是 `+0x48 == i` 的那个用户，不是列表里的第 i 个**（第二轮审查发现，`07e0aaf` 修复）。`591130(index)` 在 `5911AA` 取同一个列表，再用谓词 `5A35D0`（`cmp [pred+8], [user+0x48]`）查找；AngelScript 的 `734670` 把每个用户放到 `out[user+0x48]`（`734705..7347FC`），列表按最大序号扩长，空出来的位置留空。所以远端位按 `+0x48` 归位；没有用户对应的序号当作远端，不再因为列表短于人数就整体放弃（有人中途退出时就会出现这种情况）。**更正（2026-10-18）**：原来这里写「`591130` 在那里也找不到人，手柄号 -1 不绑定任何东西」是错的。`591130` 找不到人时返回空指针（`595960` 在 `59599C` 返回 false → `591222` `r15 = 0` → `5913EB` 返回），而 `22AB90` 在 `22AC3F` 不检查就读 `[rax+0x30]`，会直接崩溃。见下文第 4 条的修法。
   - 循环在 `22B5EC`（找不到出生点）提前退出时，不会走到最后一个序号去解除；残留的参数如果落到同一进程里下一次离线 BVM 创建上，会让离线玩家拿到 -1 或错误的分屏。现在 `Edf5BvmOnlinePlayerArgs` 每次都重复一遍 BVM 原生函数自己的联机判据（`22B34D..22B36A`），离线时一律返回 false；`MissionStart` 也会清空它。`22AB90` 只有 `22B626` 这一个调用者，所以这些参数不可能落到 AngelScript 的创建上。
   - 用户列表的释放照游戏的写法：每个 `shared_ptr` 按 MSVC `_Decref`（`+8` 减到 0 调 vtbl[0]，`+0xC` 减到 0 调 vtbl[1]），存储用游戏带大小的 `operator delete`（`12D85EC`），`>= 0x1000` 字节时取 `[ptr-8]`、大小加 0x27（`1B8DA4..1B8E1F`）。
   - 循环里的 `1F74A0` 是把玩家 `push_back` 进脚本当前的对象分组（`[rsi+0x2D0]` 是分组序号），不是镜头。
   - AngelScript 在循环之后会把 `MissionGameOverEvent` 注册为全灭事件（`1D1CB0`）。BVM 脚本自带同名函数，由脚本自己处理全灭，所以 BVM 不需要这一步。
3. ~~人数上限 4~~（2026-10-10 的做法，2026-10-18 起作废，见下一节）：会话超过 4 人时只创建前 4 个序号，第 5 人起没有角色。
4. **`22AB90` 不检查 `591130` 的空返回**（2026-10-18）：AngelScript 的单人创建 `1DC450` 在 `1DC544` 检查 `591130` 的返回值，为空时输出空玩家；BVM 的 `22AB90` 在 `22AC34..22AC3F` 直接读 `[rax+0x30]`。`591130` 返回空的情况有两种：该序号上没有用户（`595960` 在 `59599C`），或用户序号不小于游戏在线玩家记录的上限（`5959E1 cmp edi, 4`；EDF6Coop 在 `Extend=1` 时把它放宽）。修法：把 `22AC2F` 的 `call 591130` 指向 `Edf5BvmOnlineObject`。它调用原函数，返回空时改为返回一条全零的只读记录。这样 `+0x30` 控制块为空，不加锁，`12DA7AA`（`__RTDynamicCast`）拿到空指针也返回空，`22ACDC` 就走 `22AEF2` 的空玩家分支，`out = {0, 0}`。这和 AngelScript 输出的结果一样。循环在 `22B697` 看到空玩家就跳过。

## 第 5 人起（2026-10-18）

### 现象

玩家在 EDF6Coop 的 8 人 MultiSlot 房里打 EDF4.1 任务包第 3 关（4.1 包转成 EDF5 格式的 BVM，由同一个执行器运行）。第 5 人起进关后都没有自己的角色，日志写的是 `this machine's player is past the script's 4 slots`。

### 4 这个上限从哪来（静态，H）

- **不是脚本给的**。脚本只调用一次 `CreatePlayer(出生点名)`（原生 0x3E8..0x3EA → `22B1C0`），人数由执行器自己取：离线是 `GS+0x14FF4`，联机经本插件 `22B36C` 的补丁取 `GS+0x14FF8`。脚本里没有按玩家写的出生点，也没有按玩家调用的 CreatePlayer。AngelScript 任务（`M001.AC`）也是这样。
- **是执行器 `22B1C0` 里写死的 4 份东西**（不是插件自己选的）：
  - 出生点偏移：栈上 4 个 float4，`rbp+0x170..0x1AF`，`22B3C9` 初始化 4 项（`mov ecx, 4`）。常量取自 `1765B30 / 1792F20 / 1792F10 / 1792F30` = (0,0,0) / (−1,0,−1) / (1,0,−1) / (0,0,−2)，再乘以 `1765B90` = 1.0。紧接着 `rbp+0x1B0` 是栈 cookie（`22B22C`）。归一化、旋转循环 `22B490` 按人数 `r13` 次遍历（`22B477 mov rdi, r13`），读偏移的指针 `r15` 每人加 0x10（`22B59E / 22B850`）。人数大于 4 时，第 5 项会写到栈 cookie 上，再往后是保存的寄存器和调用者的栈帧。
  - 手柄号：栈上 `{0,1,2,3}`，`rbp+0x150`（`22B3B0`，常量 `1765B00`），`r12` 每人加 4（`22B585 / 22B84C`）。
  - 脚本玩家表：BVM 对象 `+0x168` 处 4 行，每行 0x18 字节（构造函数 `20DC10` 用 `12D8D44` 建，元素 0x18、个数 4）。循环按 `rdi = 序号*0x18` 写 `+0x170 / +0x178`（weak_ptr，`22B6B6..22B6C6`）和 `+0x168`（对象列表序号，`22B802`）。第 5 行会落到 `+0x1C8`，那是对象列表本身（`+0x1D0` 存储、`+0x1E0` 个数）。循环后 `22B9CB..22BA3C` 只复制 4 行（`cmp edi, 4`）。
- AngelScript 的创建 `1D9520` 也是同样的 4 项：同样的常量和缩放（`1D964D..1D9675`、`1D9682`），同样的归一化、旋转循环（`1D96B0`）。所以两个循环算出的前 4 个偏移完全相同。
- 单人创建 `22AB90` 本身不按 4 定长。序号只交给 `591130`（在线玩家对象）和 `7834F0`。`7834F0` 再交给 `7772D0`，但 `7772D0` 不读这个参数（只存 `edx`）。`591130 → 595960` 的 `5959E1 cmp edi, 4` 是游戏在线玩家记录的上限，和 AngelScript 是同一条路径，EDF6Coop 的 `Extend=1` 已经放宽它（`patches.cpp` 的 "online player object accepts index 4+"）。

### 联机注册：所有玩家同一个网络 ID（2026-10-31，4.1 任务联机时客机看不见房主在动）

- `22AB90` 的联机段 `22AFCC..22B133` 调 `7834F0(房间所有者, 玩家 weak_ptr, 是否副本(pad == -1), r9d 种子, 序号, float)`。种子是 `10AC6E0`，即脚本进程的指令指针减代码基址，也就是 CreatePlayer 所在的脚本位置。`7834F0 → 7772D0` 只用这个种子拼出 ID `{种子, 0, 0, 0}`，序号和 float 都不进 ID。一次 CreatePlayer 建出的所有玩家，脚本位置都相同，ID 也就相同。
- 注册把对象挂进房间的待处理表（`782880 → 75BE80`）。下一次房间更新由 `75BF70 → 75C030 → 75B780` 落进两张以 ID 为键的 `unordered_map`：`+0x120`（状态同步 `75D2E0` 遍历的就是它）和 `+0xC0`。两处都是查到已有的键就把值赋掉（`75B842`、`75B8D6`），所以只留下最后注册的那一个。
- 后果：房主这台按序号先建自己的玩家、后建客机副本，表里只剩副本，自己的玩家一帧都不发（房主日志里 `PLAYER sync` 一行都没有，`NETTYPE 0x03300` 的记录只有 3 B 头）。客机这台是自己的玩家后建，照常发送。
- 修复（`edf5online.cpp`）：`22B045` 的调用改道到 `Edf5BvmRegisterPlayer`，种子换成 `kPlayerNetId | 序号`（`0x80000000 | i`）。每台机器上同一序号的 ID 相同，不同序号互不相同，也不会落进脚本位置（代码偏移）的范围。离线检查 `tests/edf5_online_netid_test.cpp` 在私有映射上真跑这条注册链和房间落表，改前、改后各跑一遍。
- 同样调 `7834F0` 的还有 BVM 其他原生（`2154xx..21Exxx`，敌人和物件生成等，都把序号传给 `7772D0`），按同一个机制也可能撞 ID。这次没有处理，留作后续核对。

### EDF6Coop 怎样给原版（AngelScript）任务建第 5 人起（只读参考，`edf-coop-stable` 的 `multislot/src/mission.cpp`，v2.5.0 起相同）

- `1D968E`：归一化循环的次数从人数改成 `min(人数, 4)`（`SpawnTableCountHandler`）。
- `1D9A98`：第 i 人的偏移改由 `SpawnOffset(i, 那 4 个归一化后的偏移)` 给出。1-4 号用游戏原值；5..32 号沿 2、3、4 号的方向排，距离依次是 2 倍、3 倍……（只缩放 x、z）；33 号起在 1 号周围排成环，间距等于 1、2 号的距离（小于 0.5 时取 3），第一环半径 = 间距 × 12。
- 栈上的远端标志、MissionContext 的玩家数组都搬到插件里，长度是 kMaxPlayers；`5959E1` 等按人数的比较也放宽。
- BVM 的玩家表 Coop 不扩，只把 4 个读取点（`21F3CF / 222761 / 228AED / 22A685`）在下标 0..3 以外读成空（`BvmPlayerTableHooks`，v2.5.0 起）。

### 修法（`src/edf5online.cpp`）

照着 Coop 给 AngelScript 循环的做法，把同样的东西给 BVM 循环。不扩原版结构：栈帧大小、BVM 对象布局都不变。

| 位置 | 原指令 | 改为 |
|---|---|---|
| `22B470`（10 字节） | `lea rbx,[rbp+0x170]; mov rdi,r13` | 跳到 stub：`lea rbx,[rbp+0x170]; mov edi,4; cmp r13d,edi; cmovb edi,r13d`，再跳回 `22B47A`。归一化只做 `min(人数, 4)` 项 |
| `22B569`（17 字节） | `mov rdi,r15; lea r15,[rbp+0x170]; lea r12,[rbp+0x150]` | 跳到 stub：`mov rdi,r15`；人数 ≤ 4 时执行原来的两条 `lea`，跳回 `22B57A`。人数 > 4 时调用 `Edf5BvmPlayerLayout(rbp+0x170, rbp+0x150, r13d)`，`r15` 指向它的偏移数组，`r12` 指向它的手柄号数组，再跳回 |
| `22B69D`（10 字节） | `xor r8d,r8d; xor eax,eax; mov rcx,[rsp+0x68]` | 跳到 stub：`r14d`（序号）< 4 时执行原 3 条指令，跳回 `22B6A7`；否则跳到 `22B6E8`，跳过这一行 weak_ptr 的写入和旧值的释放 |
| `22B802`（7 字节） | `mov [rdi+rsi+0x168],ebx` | 跳到 stub：序号 < 4 时照写，否则不写，跳回 `22B809` |
| `22AC2F` | `call 591130` | `Edf5BvmOnlineObject`（上面第 4 条） |
| `22B36C` | （原有）人数 | 不再截到 4，只截到 1024（EDF6Coop 的 kMaxPlayers，即 `EDF6COOP_EXTENSION_MAX_PEERS`）；远端标志数组按 1024 分配 |

- `Edf5BvmPlayerLayout`：偏移逐项由 `Edf5BvmSpawnOffset(i, 循环那 4 个算好的偏移)` 给出。算法与 Coop 的 `SpawnOffset` 相同，所以同一个房间里 EDF5/4.1 包任务和原版任务的第 5 人起站位一致。手柄号前 4 个照抄循环自己的 `{0,1,2,3}`，之后填 -1；联机时准入门会按 AngelScript 的规则把手柄号改成本机的计数或 -1（`Edf5BvmOnlinePlayerArgs`，原有逻辑，下标上限从 4 改成 1024）。
- **确定性**：输入是同一个出生点矩阵和同样的常量，每台机器结果一样。5..32 号只有乘法。环形位置不用 CRT 的 `sin/cos`（x64 CRT 会按 CPU 选 FMA3 实现，结果可能差 1 ulp），改用自己的四分之一周归约加 Taylor 展开（`TurnSinCos`），只有加减乘除，环半径用 `sqrt`（IEEE 保证正确舍入）。
- **与 Coop 同一份实现（2026-10-18 第二轮审查）**：算法搬进 `src/spawn_layout.h`（`edf6spawn::SpawnOffset`，`#pragma fp_contract(off)`，只用加减乘除和 `sqrt`），本插件的 `Edf5BvmSpawnOffset` 直接调用它。EDF6Coop 把这个头文件原样拷成 `multislot/src/spawn_layout.h`，它的 `SpawnOffset` 也改为调用它，两边就逐位相同：AngelScript 任务和 BVM 任务的第 5 人起站在同一个点上，各机器之间也一致。`tests/edf5_online_room_test.cpp` 里有一组金标准位（11 个序号的 x/z 的 IEEE 位），Coop 的测试放同一组即可证明逐位一致。Coop 现在用 float `cos/sin`，换过来之后它的 33 号起会移动不到 1e-4 m（同一个测试里与它现在的写法逐个比对过 32..1023 号）。
- 人数 ≤ 4 时，4 个 stub 执行的都是原指令，`22B569` 也不调用插件，和改动前逐字节同路径。
- 每个跳转点都核对过：整个函数（`.pdata` 只有 `22B1C0..22BC5E` 一项）里没有分支跳到被改写的字节中间（扫描了 `22B1C0..22BE00` 的全部 jcc/jmp/call 目标）。`22B569` 的 stub 调用插件时，rsp 就是函数体的 rsp（16 字节对齐），`[rsp+0..0x1F]` 是出参影子区，此时没有活数据；之后到下一次使用前，没有易失寄存器是活的（`22B57A` 起依次重新装载）。
- ~~第 5 人起不进 `+0x168` 的 4 行表~~（第一版的做法，2026-10-18 第二轮审查起作废，见下一节「脚本玩家表的第 5 行起」）。第 5 人起的玩家照样进对象列表 `+0x1C8` 和脚本当前分组（`1F74A0`），这两个都是 vector。
- 依赖：第 5 人起能被创建出来，靠的是 EDF6Coop `Extend=1`（默认开启）放宽 `5959E1`。没有它时 `591130` 对序号 ≥ 4 返回空，现在得到的是空玩家（和 AngelScript 任务在同样条件下一样），不会崩溃，并记一行 `no player object for mission player N`。

### 全员一致：能力位（2026-10-18 第二轮审查）

每台机器都运行脚本、自己创建每个玩家，所以人数必须一致：房间里有一台旧版（只建 4 人）时，它的对象列表、脚本分组和第 5 人起都和别人对不上，而且没有任何提示。现在 >4 只在下面都满足时启用，否则**每台机器都按 4 人**，并写日志说明是谁、缺什么（`edf5online_room.h`）：

1. 本机补丁全部装上（`Edf5OnlineReady`），而且 **EDF6Coop 的 BvmPlayerTableHooks 在位**：Coop 导出了 `EDF6Coop_BvmPlayerTableHooks` 时以它为准（返回 4 个钩子位，必须全 1）；没有这个导出时要求 `EDF6CoopVersion` ≥ 2.5.0，并且 4 个点（`21F3CF/222761/228AED/22A685`）都是 Coop 自己的钩子形状（`E9 rel32` 加 `0x90` 补齐，跳到已提交的可执行内存）。每次创建时重新检测（Coop 可能在本插件之后加载，`[Mission] Extend=0` 时 Coop 不装这些钩子）。
2. **每个任务玩家的机器都向房间说过它能**：EDF6Coop 成员属性 `EDF6X_BVMPLAYERS = "1"`（本机满足第 1 条后在房间 / HQ 画面的每帧 tick 里发布，最多每 0.5 秒一次，属性在之后进的每个房间都保留；同一个 tick 也开始监视这个键）。创建时把序号 0..N-1 逐个经 `EDF6Coop_ResolveMissionPlayerPuid` 换成成员 ID，在本机的成员属性快照里找它的值，**包括本机自己**（别人读到的是同一份发布值）。旧版全军出击不发布这个键，自然判为不能。

为什么不用 `mod_room.cpp` 的 `AF_PROFILE`：那是房主建房时写的大厅属性，只能说明房主，说明不了成员；按成员公布能力的现有机制是 EDF6Coop 的成员属性（4.1 外观 `EDF6X_OUTFIT41` 用的同一套）。同时在支援协议的扩展位里加了 `kExtBvmPlayers`（`support_protocol.h`），房间里有旧版成员时，任务中的版本提示会写明「EDF5/4.1 任务第 5 人起的角色（只建 4 人）」。

一致性的边界（推测，未实机验证）：判定发生在 `CreatePlayer`，那时所有机器都已经过了 `Online_WaitStart` 的加载同步；成员属性是在房间阶段发布的，加载期间有充足时间传到每台机器（Coop 每 2 秒内发布、每秒读一次）。理论上只有「在房间里待了不到几秒就开打、加载又极快」才可能出现某台机器还没读到某成员的值，这时那台机器按 4 人、其余按 N 人，日志里会写明缺的是哪个成员。要彻底消除，需要房主在开始任务的同步消息里带上这个判定，那是 Coop 的 MissionSync，不在本插件。

### 安装：要么全装要么全不装（2026-10-18 第二轮审查）

第一版在跳转写入失败时没有回收 `AllocateNearCode` 分配的页，`RedirectCall` 的「撤销」也只是再建一个 thunk 指回原函数（字节没有恢复、又多占一页）。现在所有 stub 和被重定向调用的 thunk 都在**同一页**里；先核对全部原字节（包括每个被重定向调用的原目标），再算好每个点的新字节并记下原字节，依次写入（建循环入口 `22B36C` 最后写）；任一处写失败，已写的点按原字节逐个写回并释放那一页（写回本身失败时保留那一页，因为可能还有点跳过去，并在日志里大写写明）。`edf5_online_rollback` 测试让最后一处写入失败，核对 `EDF+0x200000..0x230000` 逐字节与安装前相同、那一页已释放。

EDF6Coop 已经知道这张表（同一处注释："filled by its CreatePlayers (22B1C0) for the split-screen players (GameStatus+0x14FF4)"），并且指出那些读取它的原生函数在联机时按 `GS+0x14FF8` 循环（`225290`）。也就是说，读取方本来就期待联机时表里是会话里的玩家，这次补上的是写入方。Coop 在 BVM 一带只改了 `179DE90 → 22BCF0`（Online_GameOverWait 的槽位）和上面那 4 个读取点，和本插件的补丁不重叠。
