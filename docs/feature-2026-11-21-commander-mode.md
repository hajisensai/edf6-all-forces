# 指挥官模式（2026-11-21）

玩家原话（2026-11-21 反馈）：

> 加一个指挥官模式，没有玩家角色，只有m视角。初始玩家生成换成玩家对应的npc角色。npc全死亡失败

## 1. 行为

开关是 ini `CommanderMode`（默认 0）。联机时由房主决定，规则见 §3。开启后，本局每名玩家都是指挥官：

| 项目 | 行为 |
|---|---|
| 视角 | 开局自动打开 M 地图。对应 NPC 入场后，按 M 在地图和该 NPC 的第三人称视角间切换。两个视角都保留指令面板并锁住玩家角色操作。 |
| 玩家本体 | 留在任务给的出生点，作为「指挥所」。它不受伤（`+0x380` bit0 NoHpLoss），敌人和锁定都不选它（`+0x380` 0x80 NoTarget，与 PvP 指挥官相同）。 |
| 对应 NPC | 开局在玩家前方 3 m 生成一名 NPC，兵种与玩家相同，拿的是玩家当前装备的武器（不降档），并且跟随该玩家。它在地图里就是这名玩家的小队，可以照常移动、攻击、警戒、集火、上车。招募小队的跟随和行军队形以该 NPC 为锚，切换视角时仍用同一锚点。 |
| 失败 | 本玩家自己的 NPC 出现过之后，如果连续 1.5 s 没有任何存活的友军 NPC 士兵，本机就让自己的玩家走原版死亡，触发原版「全员阵亡 → 任务失败」。统计的友军 NPC 包括任务自带的、支援叫来的和各玩家的 NPC。 |

NPC 兵种按 `commander_logic.h KindFor` 选。玩家当前兵种装备栏里，按槽位顺序找第一把「属于本兵种某个 NPC 模板系列」的武器，取那个模板；一把都找不到时用该兵种的默认模板：

- 游骑兵：突击步枪 / 火焰 / 火箭 / 霰弹 / 狙击，默认突击步枪。
- 翼骑兵：长枪 / 激光 / 怪物 / 雷电（Izuna）/ 雷弓，默认长枪。
- 重装兵：加农 / 中型加农 / 打桩 / 霰弹，默认加农。
- 空降兵：Root.cpk 里没有空降兵的 AI 模板（`support_call.h`），所以生成游骑兵，拿突击步枪系列里玩家拥有的最好一把；一把都没有时拿该系列最低级的一把。这是现有资源的限制，不是兼容分支。

武器取法：`npc_tier.h PickBase`。也就是降档规则里的「base」，不做 `TierDown`。

## 2. 实现

| 位置 | 内容 |
|---|---|
| `src/commander.cpp` / `.h` | 每帧逻辑，由 `map.cpp MapHumanFrame` 在本机玩家的 pre-update 里调用 `CommanderFrame`，写在 `Frame` 之前，让地图锁定当帧生效。 |
| `src/commander_logic.h` | 纯逻辑：兵种选择、请求重试 / 放弃、失败判定的防抖。测试：`tests/commander_logic_test.cpp`。 |
| NPC 生成 | 复用支援事务（`docs/support-network.md`），新目录号 `commander::kCatalog = 1020`。它位于测试场的 1021 / 1022 与任务乘员的 1023 之下，地图支援条目之上。 |
| 房主同步 | `host_settings_logic.h` 的 `m=` 字段和 `kFeatCommander`（详见 §3）。 |
| 地图锁定 | `map.h MapSetCommanderMode`。它与 PvP 的 `MapSetCommander` 是两个独立的标志：PvP tick 每帧写自己的那个，互不覆盖。 |
| 生命周期 | `mission.cpp MissionStart` 调 `ResetCommander()`：放弃上一局的引用，不删任何对象（对象归任务拆场），并松开地图锁定。 |

NPC 生成流程：

1. 请求方的 `CommanderFrame` 先读 GameStatus 槽 0 的兵种和装备（`npc_arms.h LocalPlayerLoadout`），选出 kind。
2. 联机时调用 `SubmitSupportRequest(kCatalog, 自己的位置, loadout = kind)`。请求带上 `CommanderRequesterArms(kind)`，即玩家自己那把武器。离线时本机直接建计划。
3. 房主在 `PlanCommander` 里用传输层认证过的请求者解析出它在已封存世界里的玩家士兵（`SupportAuthenticatedRequester`），在它前方 3 m 建一人计划（队长资源，`variant` 为 0）。同一名指挥官的 NPC 还在场（已建未激活，或激活后仍存活）时，第二次请求会被拒绝。
4. 各端 `ValidateCommanderPlan` 检查：模式在本机生效、单兵、属于玩家兵种的 kind、已安装、带玩家武器时武器钩子已就位、离目标 ≤ 6 m。武器在 READY 前加载（`Hooks::prepare` → `NpcArmsLoaded`）。
5. 各端 `ApplyCommanderPlan` 用同一个 NetId 生成该士兵，并先 hold 住。事务 Active 后（离线时立即）松开 hold，再让它跟随请求者的玩家：各端用计划里的请求者引用 `ResolveMarkIdentities` 解析；离线时跟随本机玩家。
6. 请求没有结果时（被拒、超时、房主世界尚未封存），每 15 s 重试一次，最多 4 次。仍然没有结果时，本玩家本局放弃指挥官模式：还原保护位，松开地图锁定，写日志。

失败判定：每 250 ms 做一次原生全队伍遍历 `0x5E0C80`。

- 有 lobby user（`+0x1ED0`）的 Soldier 是玩家（各端的玩家都在内），给它们加保护位。
- 没有 lobby user、未死（`+0x2E8`）、未从场景删除、队伍为本玩家队伍或 2 的 Soldier 计为友军 NPC。

各端遍历的是同一批同步对象，所以会得出同样的结论，各自杀死自己的玩家（本机是自己玩家的权威端）。

### 2.1 原版死亡（静态逆向，2026-11-21）

判负时让本机玩家吃一次原版伤害，后续全部交给原版：死亡、联机同步，以及任务脚本自己的「全员阵亡 → 失败」（`MissionGameOverEvent`，联机走 `Online_GameOverWait`）。MissionResult 没有「失败」值（0–5），所以不用 `MissionMgr::End`。

- **入口。** `SendMessage 0x1DA480(obj, u32 msg, void* data)` 依次调对象的槽 10、9、11，伤害队列也这样发（`0x543AB9`，消息 `0x10000000`，data = 队列条目里的 GameDamageInfo）。
  - GameObjectBase 槽 9 `0x54A530` 在 `0x54A555` 做 `add edx,0xF0000000; cmp edx,0xF`，所以 `0x10000000` 走 case 0（`0x54A579`），调 ApplyDamage `0x547C30(obj, gdi)`。
  - 死亡边沿（+0x2E8）上它会发 PlayerDown，并写 `gdi+3`，所以 GDI 必须可写。
  - 士兵槽 9 最终都进这个 case：AssultSoldier / PaleWing / Engineer 是 `0x598FD0`，HeavyArmor 是 `0x567250`，两者都经 HumanBase `0x572810` 原样转进 `0x54A530`。
- **GDI。** 共 0x90 字节，ApplyDamage 和士兵各槽都不读 +0x90。

  | 偏移 | 填写 |
  |---|---|
  | +0x24 | 攻击方队伍 -1（不做友军判断） |
  | +0x10 / +0x18 | 攻击者为空（整段跳过） |
  | +0x30 | 士兵位置 |
  | +0x50 | 有限的伤害值：最大 HP × 1000。用 FLT_MAX 时，倍率连乘可能出现 inf×0 = NaN，`minss/maxss` 会把 HP 夹回满血。 |
  | +0x60 | `0x40`（forced：越过槽 16/17、`+0x380` bit0 与 0x800）。不能带 0x200。 |
  | +0x78 | 指向一条有效的 0x30 字节命中记录。`0x54E400`、`0x5987DB` 会不看数量直接读它，**不能为 null**。 |
  | +0x88 | 0 |

- **联机。** ApplyDamage 里的联机判断 `0x7748F0` 不看对象，只看是否在会话中。HP 在哪台机器调用就在哪台扣，所以只对本机自己的玩家调用：有 pad（`+0x340`），`+0x128` bit0 为 0。
  - 死亡由该士兵自己的网络消息 0x11 送出（槽 40 `0x59D2B0`）。
  - 接收端走槽 41 `0x577020`，这正是原版联机里玩家倒下的方式。
- **加载时校验。** `KillLocalPlayer` 检查上述函数头和 switch 的字节，并检查该士兵 vtable 的槽 9 是 `0x598FD0` 或 `0x567250`；不符就写一行日志、不判负。
  - 调用后若 +0x2E8 未置位（脚本设了最低 HP，或受伤倍率为 0），只记日志，不重试，也不直接改 HP。
  - 离线审计：`tests/commander_native_audit.py`（需要 `EDF6_NATIVE_DLL`）。
- **顺带发现（不在本次范围）。** `src/edf41classes.h` 的 `kMsgDamage=0xF0000000` 到不了槽 9 的伤害 case（`0xF0000000+0xF0000000=0xE0000000 > 0xF`）。按槽 9 判断这个值的 hook（如 `primer.cpp`）需要另行核对是否从未命中。

## 3. 联机

- 房主字串新增 `m=<0|1>`，当前格式为 `3;v=…;f=…;r=…;c=…;m=…;s=…`，并新增特性位 `kFeatCommander = 512`。
- 本局是否开启，在 MissionSync 时由 `CommanderAtSync` 决定一次，整局保持不变：
  - 房主：以自己的 ini 为准。
  - 客机：以房主发布的字串为准；房主没有发布字串（旧版）时关闭。
  - 无论哪一方，都还要求房间已读取成功、所有成员都发布了字串、并且都带 `kFeatCommander`。只要有一名成员的版本没有这个功能，本局全员都是普通模式。房间提示里会列出「指挥官模式」这一差异项。
- 离线时，在任务开始（`HostSettingsOfflineMission`）读本机 ini。
- 旧版本成员的处理遵循仓库规则（联机要求全员同版本）：不写兼容分支，只关闭本局的指挥官模式。
- PvP 对局中不生效：`ReadPvpStatus().enabled` 为真时本机不开启，房主也拒绝这类计划。
- 每名玩家各自请求、各自拥有一名 NPC。NPC 的 AI 和伤害结算照支援士兵的规则由房主负责；地图指挥走现有的 `command_net`，客机照常能指挥自己的小队。
- 保护位在每台机器上都打在所有玩家身上：敌人 AI 在房主机上选目标，伤害在各玩家自己的机器上结算。

## 4. 已知限制与风险（实话）

- **玩家本体仍然存在。** 游戏的任务脚本、镜头、地图和联机成员表都以玩家士兵为中心（地图由玩家士兵的 pre-update 驱动，`map.cpp`），所以不能真的不生成玩家。现在的做法是让它留在出生点、不受伤、不被选为目标、不接受操作。它仍然可见、有碰撞，NPC 和载具可能绕开它。隐藏模型和关碰撞没有现成的、逆向过的路径，本次没有做。
- **NoTarget 对 AI 的实际效果未实机验证。** PvP 指挥官用的是同一个位，`docs/plan-2026-10-25-pvp-factions.md` 也标注「未实机」。
- 友军 NPC 的统计依赖原生队伍登记。坐在载具里的 NPC 是否仍留在登记表里，静态分析认为是（玩家坐车时仍被 `mission_participants` 找到），但没有实机核对。如果载具里的 NPC 不在表里，「全员上车」会被误判为全灭。1.5 s 防抖只挡得住瞬时的进出，挡不住这种情况。
- 任务自带的友军 NPC 也计入「全灭」，所以有自带友军的任务比只有指挥官 NPC 的任务更难失败。这符合「npc全死亡失败」的字面意思。
- 空降兵的 NPC 是游骑兵（见 §1）。
- 全部是离线检查（`tools/check.py`）。**没有实机测试**：生成、跟随、地图锁定、判负都需要实机确认。

## 5. 待实机确认清单

1. 离线开启后进任务：地图自动打开、关不掉；出生点前方出现对应兵种的 NPC，拿的是玩家的武器（日志 `COMMANDER spawn`、`COMMANDER arms`）。
2. 敌人不攻击玩家本体（NoTarget），本体不掉血。
3. NPC 在地图里显示为本玩家的小队，各条命令都可用。
4. NPC 全部阵亡后 1.5 s 左右玩家死亡，出现原版任务失败画面。
5. 联机两人：各自生成自己的 NPC；客机能指挥自己的 NPC；全灭后两端都判负。
6. 有成员把 `CommanderMode` 设成 0（房主设成 1）时，本局全员按房主的设置开启；有旧版本成员时全员关闭，房间提示列出差异。
