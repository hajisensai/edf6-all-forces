## 1. 「炮塔不会随着车体旋转而旋转」→ 炮塔转速应叠加车体转速

用户澄清（2026-10-09）：「我只是想让炮塔旋转速度应该叠加底座旋转速度才合理。」炮塔装在车体上，方向机的最高转速是**相对车体**的，
车体转动把炮塔一起带着转：炮塔世界角速度 = 车体偏航角速度 + 相对车体的电机转速（电机转速被方向机上限夹住）。瞄准目标仍是
战雷式镜头给出的世界方向（镜头航向保持世界坐标），稳定器仍让炮塔追世界目标。

> 第一版提交 `a74a092` 误解为「炮塔航向跟车体走、稳定器只抵消颠簸」，加了 `TurretFollowsHull`、镜头航向跟随和稳定器 `Follow`。
> 本次提交全部撤掉（`stab.h` / `stab.cpp` / `turretcam.cpp` / `turretcam.h` / `crew.h` / `plugin.cpp` / ini / `stab_check` /
> `stab_native_readback_test` / `docs/camera-re.md` 回到 `b89d26a` 后再改），README 对应句子删掉。

### 限速实际在哪里生效（根因）

- 原生轴步进 `0x5FBC00`（`turretcam.h AxisStep` 复刻）：轴角是**相对车体**的，速度按输入缓动、最高 `+0x90[2]` rad/帧。没有稳定器的
  炮位这就是全部：炮塔镜头按世界目标求输入，车体转动天然叠加，已经符合用户的模型。
- 有稳定器的炮位（`stab.cpp kClasses`：Blacker / Titan / 601 / E551 / Kepler / Grape 主炮，坦克和机甲的炮手座）多了 `stab.h Step`：
  它在世界里存参考线，**只有指令（原生这一步自己的转动 `own`）移动参考线**，再加修正 `c` 抵消车体转动；`own + c` 被夹在方向机
  最高转速内（相对车体，这一点本来就对）。问题在参考线：指令以 ≤ 最高转速推着**世界里的**参考线走，车体朝目标转时 `c ≈ −ω`
  把车体帮的那部分转回去，炮在世界里最多只能以方向机最高转速转——上限实际落在了世界系里，车体转动没有叠加
  （HEAD `stab.h:151-155` 的 `own` / `c` / 夹取，参考线只在 `:144-146` 由指令推动）。离线复现：0.5 rad/s 的方向机、车体以 0.3 rad/s
  朝目标转，旧模型炮的世界最高转速 0.500 rad/s。
- `turretcam.cpp Steer` / EDF6AutoTurret 从 `StabHeld`（参考线换算到本帧的轴角）求下一步输入，并把车体那部分从目标变化率里扣掉：
  前瞻读的就是参考线，所以 Step 改参考线、Held 自动保持同一模型，不需要另改。

### 修法（`src/stab.h Step`、`src/stab.cpp`）

- `Hold::full[2]`：本步指令输入是否打满（|输入| ≥ 0.999 取 ±1，`stab.cpp FullOf`，从瞄准步的输入 `in` 读）。
- Step 每根轴：指令打满、且修正 `c` 与指令方向相反（车体正朝指令方向转，稳定器要把它转回去）时，不做这次反向修正（`c = 0`），
  参考线直接放到炮这一步的实际轴角上（`t = after`，`moved`；整合审查：最初写的 `t -= c` 只按增益 k 补差，参考线稳定落后炮「车体转速 × lag」，输入从打满回落那一帧稳定器会把炮往回拉、前瞻也看到这个滞后）：轴在车体上照指令的原生转速走，炮在世界里 = 指令转速 + 车体转速，相对车体仍不超过
  方向机上限（`own` 本身由原生缓动限住）。
- 车体反向转：修正与指令同向，照旧夹在方向机上限内；车体转得比方向机快时炮被带偏，误差超过 20° 由原有 `slip` 拖动参考线。
- 没打满（接近目标的小修正、保持不动）：与以前完全相同，稳定器照常守线、抵消颠簸。车体静止时 `c ≈ 0`，行为逐帧不变。

### 测试（`tools/stab_check.cpp HullAddsToDrive`，炮塔镜头控制器 `SteerAxes` + `Held` + `Step` 闭环，方向机 0.5 rad/s，目标在左 120°）

- 车体静止：最高 0.500 rad/s、第 269 帧对准，与关掉 `full`（旧模型）逐项相同。
- 车体以 0.3 rad/s 同向转：炮的世界最高转速 0.800 rad/s（= 0.5 + 0.3），第 177 帧对准（旧模型 0.500 rad/s、第 271 帧）。
- 车体以 0.8 rad/s 反向转（快于方向机）：2 秒时误差 154°，炮被带偏。
- 目标固定、车体 ±0.3 rad/s 蛇行：最后 1 秒误差最多 0.026°（蛇行快于方向机时会被带偏，属物理合理，不作断言）。
- 原有 bumps / camera / outrun / gunner / stops / 读回契约检查全部照旧通过；`stab_native_readback_test`（真实 EDF.dll）照旧通过。
- 变异实测：让 Step 里的叠加分支永不触发 → 「同向转时世界转速 = 方向机 + 车体」「同向转更快对准」2 条失败。

## 2. 「钻头战车的车体少了贴图」

### 根因

`pylib/drill_model.py`（HEAD `:55-56`）只给 `MI_Tank_C`（车体上部和钻头）配了 `Tank_C_BC.png`，`MI_Tank_B_CS`（下半个车体、负重轮、
履带，y 0~1.85 m，车体 10.6 万顶点里的 7.3 万）被当成「贴图没随模型提供」画成 4×4 的纯色深钢灰（`SOLID`）。读已安装的
`Mods/OBJECT/EDF6VC_DRILL.MRAB` 确认：`edf6vc_drill_b` 的 albedo 就是那张纯色图。

但 `Tank_C_BC.png` 本身就是两种材质共用的图集：把 `MI_Tank_B_CS` 的 UV 画到图上，负重轮、诱导轮、履带条、十字件、左侧大块侧板
都和图上 `MI_Tank_C` 从不使用的区域（左下角的轮子 / 履带行、左侧板）逐个对齐；按 256² 网格栅格化 UV：`MI_Tank_C` 覆盖图集 26.6%，
`MI_Tank_B_CS` 38.9%，两者合计 58.4%（两倍多）。打包没有问题（成员、.lod、顺序都对），问题在生成器的材质表。

### 修法

- `MATERIALS` 表：OBJ 材质 → （游戏材质名，albedo 源文件），两种材质都用 `Tank_C_BC.png`；`ALBEDO_TEX` 每个源文件只打包一次
  （档案大小不变，4.23 MB）。原版 Blacker 那 5 个没有网格画的材质改用独立的 `edf6vc_drill_steel.dds`（以前借用 `_b` 的纯色）。
- `drawn_albedo_problems` 并入 `check()`：每个有网格的材质必须是 OBJ 材质、albedo 必须是它的图集，纯色钢板会被拒绝。
- `texture_coverage`：上面那组覆盖率的离线计算，作为「同一图集」的证据进测试。

### 测试

- `tests/drill_model_rotation_test.py`：MATERIALS 每项都有贴图；有私有 OBJ 时覆盖率断言（B_CS > 0.3、合计 > 1.6 × C）；
  `--archive` 时 `drawn_albedo_problems` 为空，并把下半车体改回纯色钢板做负对照（必须报错）。
- 用新生成器离线生成（`python tools/make_drill.py <游戏目录> --out tmp/out`）通过 `check()`；同一检查对**当前已安装**的旧 MRAB 报
  `material edf6vc_drill_b: albedo edf6vc_drill_b.dds, want the atlas edf6vc_drill_c.dds`（就是用户看到的问题）。
- `pylib/model_view.py --color @tex` 渲染新旧两版对比：旧版下半车体纯深灰，新版是和上半车体同一套蓝灰涂装与轮子 / 履带颜色。

## 3. 钻头战车的发射

### (a) 「发射钻头的时候没伤害，回收的时候有」

**根因**：`src/drill.cpp SweepEnemy`（HEAD `:643`）飞行中只咬「身体（脚下 / 锁定点 / 中点）离钻头轴线 ≤ 半径 1.55 + 1 m」的敌人。
钻头从车上沿车头方向平飞，轴线离地 4.21 m；地面敌人的脚在地上、锁定点约 1 m 高，离轴线 3.2~4.2 m，**永远够不到**——这正是
2026-10-05 车头近战犯过的错误（`docs/drill-re.md` §5.5：围着高处轴线的圆柱碰不到在犁的敌人），飞行判定又用回了圆柱。
用户看到的「回收时有伤害」其实是钻头接住后车头近战探测恢复、转速还在最高，立刻咬了车前的敌人。

**修法**：飞行的够得着范围 = 车头接触箱随钻头带走：在钻头自己的坐标系（原点在根部、z 轴线、y 为车辆上方正交化）里
x ±2.4 m、y 从轴线下 4.21 m（发射时的离地高度，一直到地面）到轴线上 1.55 + 0.3 m、z 从根部到尖端前 1 m，敌人身体段
（脚下..锁定点，加 1 m 厚度）与箱相交就算；多个时取离轴线最近的。`BodyInBox` 与车头近战的 `SeeEnemy` 共用；钻头的坐标轴
`FlightRows` 与画飞行姿态的 `PoseFlight` 共用（原来各算一遍）。离车 7 m 内不咬的规则不变。

### (b) 「为什么钻头发射的时候还会受到左键的控制是否旋转」

**根因**：飞行中 `held` 被强制为真（HEAD `drill.cpp:785`），但转速是从发射那一刻的值按 `DrillSpinUpSec`（1.8 s）慢慢升上去的；
`Launch`（HEAD `:573` 附近）不动转速。没按住射击键就发射，钻头飞出去时几乎不转、整个去程（约 1.7 s）都在加速——看起来像
「按没按左键决定它转不转」。

**修法**：`Launch` 时转速直接置为最高（喷气驱动的自转），飞行中保持最高、与射击键无关；只有过热会让它减速（与扳机无关）。

### (c) 「钻头为什么有25的弹药」

**根因**：钻头这件武器 `EDF6VC_DRILL_BIT.SGO` 由 `tools/make_drill.py bit_sgo` 从原版 Blacker 炮 `V_505TANK_CANNON01.SGO` 改出，
`BIT`（HEAD `make_drill.py:69`）没改 `AmmoCount`，沿用了炮的 25 发弹匣（离线读生成的 SGO：`AmmoCount 25.0`），原版 HUD 和插件 HUD
都读武器的实时弹数（`+0xBE8`）显示 25。

**修法与依据**：钻头只有一个、可回收，所以弹数语义 = 发射-回收循环：`BIT` 加 `AmmoCount: 1.0`（`check()` 随 BIT 一起核对）；
插件 `KeepRound` 每帧把实时弹数保持为 1；钻头在不在车上由 HUD 钻头行的 LAUNCHED / RETURNING 表示。

整合审查后改过：第一版发射期间写 0。逆向原版对 0 发的反应（EDF.dll `678CCB46`）：
- 换弹：武器每帧更新 `0x6934F0` 在 `0x693B2F` 判 `ReloadTime`（`+0x20C`，`0x68C9DD` 由 SGO 四舍五入写入）< 0 就跳过整个装填块；钻头的 `ReloadTime` 是 −1 → `+0x20C = −1`，0 发**不会**进换弹状态机，但也**永远不会自己补回**（射击路径 `0x69820E` 扣弹）。
- 开火门：`0x693FC6` 要求弹数 > 0，0 发时武器不能开火。
- NPC 选武器：武器类之外读 `+0xBE8` 的只有 `0x567811`、`0x5A1F75`，两处走的是士兵自己的武器表（human `+0x1970` / `+0x1980`），不是载具的；NPC 驾驶的钻头战车从不发射，弹数一直是 1。未发现载具 AI 按弹数换武器（505 只有这一件武器）。
- 插件 HUD：所有武器 0 发且不能装填时 `hud.cpp` 显示红色 EMPTY 和 NO AMMO 告警——这是第一版写 0 的真实副作用（飞行中误报弹尽）。
所以改成恒为 1：既去掉误报，也让 NPC AI 偶尔扣掉的那一发（不会自己装填）下一帧补回。
写实时弹数与 `heli.cpp` / `emc.cpp` 已有做法相同。

## 未实测（需要进游戏看）

1. 炮塔转速叠加：开 Blacker 等有稳定器的坦克，鼠标甩到侧后方大角度目标的同时朝该方向原地转向，炮塔应明显比车体不动时快；
   反向转向时变慢，车体转得快时炮塔暂时追不上、车停后追回。打满判据用的是瞄准步收到的输入（炮塔镜头远处给满输入、鼠标每帧最多
   ±1），手柄半推摇杆时不打满、稳定器照旧守线，这种情况下的手感未实测。
2. 指令刚从打满回落时参考线已随车体多走了一段，炮塔镜头下一帧从新的守住角度重新求输入；离线闭环没有过冲，实机未看。
3. 钻头战车下半车体的贴图是否正确对齐（离线只做了 UV / 图集覆盖分析和顶点采样渲染；不同区域有少量 UV 与图案并不完全吻合的地方，
   铁雨原作是否另有一张 `Tank_B` 贴图无法离线确认）。**需要重新运行安装器**生成新的 MRAB 和 BIT SGO，只换 DLL 不会变。
4. 发射中钻头掠过地面敌人时是否掉血、击杀降温是否计入；装药从敌人往钻头方向退 2 m 起爆，敌人在钻头正下方 3~4 m 时装药起点在

5. 弹数显示：原版 HUD 是否显示 1 / 0；把实时弹数写成 0 时原版 505 的装填逻辑（`ReloadTime -1`）是否有副作用（静态未追到写入点）。
