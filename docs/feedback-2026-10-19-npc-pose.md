# 2026-10-19：NPC 武器姿态资源契约

用户报告了两种画面：红盔游骑兵的步枪横在胸前；旧式士兵把长武器抬到头顶。第二张画面中的 `不明な再生キー` 属于字幕键解析，见 `edf41-caption-contract-re.md`，不能据此认定 CAS 动画键丢失。

## 已证实的资源问题

旧 EDF4.1 友军保留了自己的骨架与 CAS，却按同名路径加载 EDF6 重新导出的枪械模型、动画与 MAB。此前仅用左腕绑定姿态差计算一个 `soldier_weapon_grab_adjust`，属于近似坐标补偿：已有数据检查允许游骑兵约 8–17 度、飞翼约 12–30 度的剩余旋转差，也没有验证动画过程中的差值恒定。

支持版本 EDF.dll 的 `0x597F00..0x59823A` 实际计算为：

```text
left_hand_target = soldier_weapon_grab_adjust * weapon_MAB_IK * weapon_node_world
```

其中 MAB 定位点与节点矩阵都属于当前这把枪的模型。一个模型的绑定腕旋转，无法代替每把原枪的实际 IK、骨骼挂接和动画。`human_direction_adjust` 的原有轴修复仍成立：`0x575514` 的 mode 2 围绕局部 X，其余模式围绕局部 Y；原 4.1 脊椎局部 Y 朝上，继续使用源 mode 1。

## 实现

`tools/make_edf41_objects.py` 的 `friend_weapon` / `friend_weapon_contract` 把每个友军的原武器、原模型、原 CAS 和原 MAB 作为完整资源组生成。

- 26 种 4.1 任务友军与 2 种 Omega 队员均引用 `WEAPON/EDF41_NPC/` 私有路径。
- 实际检查的 19 种源 NPC 武器全部存在于 EDF4.1 原安装，没有用相似武器代替缺失来源。
- 使用 `edf5port.weapon41` 做格式转换，补齐 EDF6 的字段及五种语言名；保留源 HOLD、武器类、参数和 MAB。不会调用面向 EDF6 玩家骨架的 `hold_as` 或借换 MAB。
- 音效的四种字段检查 EDF6 常驻银行：仅源 cue 缺失时，采用同名原生 AI 武器同字段、相同触发模式的常驻 cue，保留其余播放参数。实际只有 `AILAZR02` 从非必装 4.1 声库的 `weapon_WD_MEDIUM_lazr197` 改为常驻 `weapon_WDAI_MEDIUM_lazr197`，双方循环标志均为 1，避免未装 4.1 音频时失声。
- 原枪的 RAB、CAS、弹壳 RAB/SHKT 也放在相同私有目录，避免同名资源被 EDF6 重制版替代。HUD 瞄具和图标使用原生显示资源。
- 有源 `soldier_weapon_grab_adjust` 时保留；当前所有源 NPC 均没有此键，因此以单位矩阵直接使用原 MAB/IK，移除先前约 84 度的绑定腕补偿。
- 对 main stance、武器 player 的 aim/change/reload，以及嵌套的盾牌和打桩技能键，比较源与移植后的实际 CAS，禁止增加未解析动作。源数据本就缺少字面同名状态的 `waist_recoil_M` / `shield_bash` 等，不擅自补猜测动作别名。
- 安装沿用 `edf41` 所有权、现有资源闭包与材质兼容流程。未写入任何游戏目录。

生成结果：28 种友军、19 种私有武器、48 个私有资源，未压缩资源合计 7,823,074 字节。资源包继续使用成员去重，`objects.json` 的 SHA-256 与每个对象依赖列表同步更新。

## 「NPC有的会立正」：4.1 友军卡死在 EDF6 的翻越状态（2026-10-19 晚）

用户原话：「NPC有的会立正」（补充：「立正只是比喻」）。截图是 EDF4.1 战役的城镇任务（广播在说巨型昆虫巢穴与四足要塞），近处一名蓝甲狙击游骑兵（由 4.1 蓝甲与狙击枪推断为 `OBJECT/EDF41/AIARMYSOLDIER_SN.SGO` 一类的 4.1 友军，M：4.1 的模型、骨架与 CAS）身体直挺、枪斜举在胸前，不动也不打。

### 根因（EDF.dll 0x678CCB46 静态，H）

- 4.1 友军的 SGO 以 EDF6 同名文件为模板，只换 4.1 的外观与武器（`FRIEND_KEYS`），所以保留了 EDF6 的 `human_climb_settings`：26 种 LOOKS 友军全部带着它，Omega 队员经 `fill_class_keys` 也被补上（四个士兵类的每个原版 SGO 都有这个键）。
- 有这个键，士兵类就会翻越障碍（`0x56F0E3` 读键，`0x56F8BF` 建 `human+0x1298`）。移动中的障碍检测 `0x57BF90`（`0x56E067` / `0x57B675` 调用）对 NPC 同样生效（slot 49 `0x598F00` 对没有手柄的士兵返回 1），进入翻越状态 slot 72 `0x5790A0`。
- 翻越状态按障碍高度播放 `common_elude_large_up / middle_over / middle_up / small_up` 之一（索引在 `0x5784D4..0x578543` 一次性解析到 `+0x1530..+0x153C`），动作限制写成 `0x62D`（`0x5791DA`，全代码唯一写这个值的地方），**只有主播放器当前状态播完（`0x5798DF` → `0x116BBE0`）才回到普通状态**，没有超时。
- 4.1 的三个士兵 CAS（`ARMYSOLDIER.CAS`、`HEAVYARMOR.CAS`、`PALEWING.CAS`）一个翻越状态都没有（EDF6 的三个都有四个）。索引是 -1，播放 `0x116BFC0` 对 -1 直接返回 false、不改状态，主播放器继续放进入时的走路循环；走路是结束类型 0，结束时间 -1.0（`0x116C2B3`），`0x116BBE0` 永远不为真。于是士兵永远停在翻越状态：原地不动，插件和原版 AI 写的移动都被忽略，姿态停在走路的持枪姿势——就是截图里的「立正」。
- 城镇地图到处是 0.25–3 m 的台阶、围墙、栏杆（`max_step_height` 3.0），所以「有的」会卡：碰到障碍的那几个。
- 之前把「翻越」当成可以缺的闪避（`friend_states` 注释：缺状态只是保持原状态）是错的：其他缺失状态确实如此，但翻越是要等它播完的状态。

### 修复

`tools/make_edf41_objects.py`：

- `SOLDIER_CLIMB_KEY` / `SOLDIER_CLIMB_STATES` 记录上面的契约；`drop_climb`：士兵 CAS 主播放器一个翻越状态都没有时，从 SGO 去掉 `human_climb_settings`（4.1 原版的士兵本来就不会翻越）；只缺一部分时拒绝生成（哪个高度挑哪个动作由障碍决定，无法替换）。LOOKS 友军与 Omega 队员两条路径都调用。
- 去掉这个键是原版支持的形态：`+0x1298` 的所有读取点都先判空（`0x56FCC0`、`0x56FCE0`、`0x57BF9F`、`0x596CCA`、`0x596E4B`、`0x5A0E5C`、`0x5A0ECC`、`0x5A0F3C`），寻路的可翻越高度随之为 0，不会规划需要翻越的路线。`NULL_CHECKED_KEYS` 让 `check_class_keys` 允许四个士兵类缺这个键。
- `CLASS_NAMES` 新增 `when_key`：带 `human_climb_settings` 的士兵，CAS 必须有全部四个翻越状态，否则构建拒绝——以后任何移植士兵再带上这个键都会被挡住。
- 不做的事：不把翻越状态别名成 4.1 的其他动作。翻越的位移来自动画（更新里读主播放器的根运动，`0x1167030` / `0x1166A40`），拿没有对应根运动的动作顶替只会让士兵原地「翻」完又被同一障碍挡住、反复进入。

`src/npcai.cpp StuckClimb`（只读诊断，不改士兵）：一名 NPC 的动作限制持续等于 `0x62D` 超过 4 秒，记一次 `NPCAI <类> <指针>: held in the climb state N s at (...); its CAS's climb states a b c d`，四个数是 `+0x1530..+0x153C`，-1 即缺状态、永远出不来。每段只记一次。

### 验证

- `tests/npc_climb_native_audit.py`（有 EDF.dll 时）：44 项字节核对，覆盖上面每个地址、四个类的 slot 72 / 49、`0x62D` 的唯一写入点和插件常量。
- `tests/edf41_npc_climb_test.py` + `tools/selftest.py edf41_friend_climb_shipped`：已提交的每个士兵 SGO，CAS 缺翻越状态就不能带这个键；28 名 4.1 士兵都不带；把键加回去的变异被拒绝；`without_key` 只去掉这一项。
- 重新生成的 `edf41port/` 与生成前的差异只在 28 个士兵 SGO 及 `objects.json` 的对应哈希（生成前先用未改的工具重跑一遍，与已提交文件逐字节相同）；`src/enemy_control_ported_spawn_profiles.inc` 随之由 `tools/gen_enemy_control_ported_spawn_profiles.py` 重新生成（只有哈希行变化）。

## 2026-10-20 审查：第 16 条截图是原生 NPC，#225 未覆盖

审查核对后，第 16 条（「NPC有的会立正」）截图里那名 NPC 是城镇任务里的**原生 EDF6 NPC**，不是上面推断的 4.1 蓝甲狙击游骑兵。#225 的修复（4.1 友军去掉 `human_climb_settings`）对它不起作用，**原生 NPC 的「立正」未修**。

静态排查（EDF.dll 0x678CCB46）：

- 上面那条卡死机制要求 CAS 缺翻越状态（`+0x1530..+0x153C` 为 -1）。原生士兵用 EDF6 自己的 CAS（`EDF6ArmySoldier.cas` 等），四个翻越状态都有，翻越会正常播完退出，所以不是同一个根因。
- 翻越状态的唯一出口仍是 `0x5798D2..0x5798E6`：`0x116BBE0(human+0xB90, [human+0x1420])`。它在该轨记录（`[player+0x60] + track*0x160`）的状态 `+0x104 == -1` 时为真，`+0xF0`（结束）< 0 时永远为假，否则 `+0x100 + +0xE8 >= +0xF0` 时为真（`0x116BBE0..0x116BC22`）。也就是说，即使 CAS 齐全，只要翻越期间那条轨被换成了循环动作（结束 < 0），士兵也会永远停在翻越里。插件自己不播 NPC 的 CAS 动作：背包武器的使用被动作限制 bit 2 挡住（`npc_backpack.cpp kStateNoPack`，翻越的 `0x62D` 带这一位），其余写的是意图块（移动、视角、扳机）。谁会在翻越期间换掉那条轨，静态找不到。
- 其他候选（未核实，沿用上面的清单）：原生 appeal 姿态、插件转身意图 `d64` 与原版增益不同导致的 `v_turn_speed` 突变。

现在做的：`npcai.cpp StuckClimb` 的诊断日志（对本机运行 AI 的每名 NPC，原生的也在内）多记一项：卡住时主轨编号、它正在播的状态、`+0x100` / `+0xE8` 与结束 `+0xF0`。下一次原生 NPC 卡住时，日志 `held in the climb state ... main track N plays state S ... end E` 能直接说明是缺状态（-1）、是循环动作顶掉了翻越（E < 0），还是根本不在翻越里（没有这条日志）。需要实机回传带这条日志的 `EDF6VehicleCrew.log`。
