# 2026-10-25 反馈：4.1 第一关打着打着变成灰白地图

用户原话：「4.1任务第一关…打着打着会变成灰白样子地图」。地址均为 EDF.dll TimeDateStamp `0x678CCB46` 的 RVA。
H = 实机或反汇编直接证据，M = 推断。

## 结论

V301 坦克（4.1 的 `Vehicle301_Tank_ai`，跑在 EDF6 的 `Vehicle601_Tank` 类上）开始瞄准后，炮管骨骼的矩阵每帧被再转一次、
不断累积，约一秒内长到 1e20 以上；这个包围盒经 Umbra 的输入进了 Umbra 的空间数据库，把它整个毁掉：近景、阴影、远景从此
几乎查不出任何物体，画面只剩天空、HUD、粒子和第一人称手里的枪，直到任务结束。根因在转换链：`pylib/edf41tank.py` 给 V301
做的 CAS 只留了炮管后坐（`cannon_slide`）一条轨道，丢了 `cannon` 的静态轨道，而 601 类每帧是「就地」转 `cannon` 的。

## 证据链

1. **画面不是相机、裁剪面或地图掉落（H）。** VIEWDIAG 一直 ok（眼位在地面上 1.8 m、近景 0.1..3000、远景 500..35000）；
   两份灰白转储里相机矩阵、视锥平面都正常、无 NaN。
2. **Umbra 几乎什么都查不到（H，灰白时实机断点）。** 在 Commander 回调 `0x11E2120` 上计数：正常时主视角每帧收集 64+约 10
   个对象（`0x11E3E24`，`getDataCount`），G-buffer 列表约 70；灰白后每帧只剩 1~6 个（全是移动中的蚂蚁，`0x17A8F70`），
   阴影视图（视图 2）一个都没有。Umbra 统计 `STAT_DATABASEOBSVISIBLE` 24 帧只涨了 26。阴影不做遮挡查询，所以不是硬件
   遮挡查询的问题，是空间数据库本身。
3. **出事前 Umbra 收到一个越界的盒子（H）。** 测试插件探针（`tests/autopilot/umbra_probe.cpp`，换 EDF.dll 对
   `Object::setObjectToCellMatrix` 的导入 `0x17567D0`）：每次灰白前恰有一个对象的矩阵越界，平移 1e8~1e22、轴被
   `0x11B30C0` 夹到 1e6；调用路径 `0x11B32F8 ← 0x6C06F7 ← 0x630235 ← 0x674A21`（载具模型更新），归属
   `Vehicle601_Tank`，骨骼 4（`cannon`）、5（`cannon_slide`）的矩阵越界。出现时刻 = 灰白开始时刻。
   `0x11B30C0` 只夹轴长、不夹中心也不拦 NaN。
4. **炮管在转（H）。** 同一探针每 0.25 s 记 601 的座位 0 瞄准轴与炮管姿态：不瞄准时炮管姿态稳定（行长 1.00002）；
   一旦俯仰命令不为 0（-0.013 rad 起），炮管绕 x 轴连续旋转（-0.08 → -0.39 → -1.09 → -2.2 → 绕过 ±π 继续，
   约 4~5 rad/s），矩阵行长 1.00003 → 1.0013 → 1.022 → 1.18 → 2.1 → 9.7 → 1964 → 6.5e7，接着越界、之后 NaN。
5. **为什么会转（H，反汇编）。** 601 的 slot 45 `0x620830`：`0x6EDCA0`（物理写骨骼）→ `0x661C00`（炮塔）→
   `0x661810(veh, 炮骨, 炮塔骨, 俯仰)`。`0x661810` 取炮骨记录的 `+0x70`（`lea rdi,[rdx+0x70]`，`0x661886`），
   乘炮塔矩阵、绕 x 转俯仰角（`0x296F90`），再乘炮塔逆矩阵**写回 `+0x70`**（`0x661BCC..0x661BEF`）。转的是绝对俯仰角，
   所以必须每帧先从 CAS 轨道把 `+0x70` 复位：EDF6 自己的 `V601_TANK.CAS` 两个片段里每根骨头都有静态轨道（含 `cannon`）。
   V301 的 `EDF41_V301_RECOIL.CAS` 只有 `cannon_slide`：`cannon` 的 `+0x70` 保留上一帧转过的结果，每帧再叠一次俯仰角，
   浮点误差随之指数放大。炮塔骨 `0x661C00` 只读 `+0x70` 不写回，不受影响。
6. **对照（H，实机，M190 后台跑，`probe umbra` 计越界次数）**：
   | 配置 | 跑次 | 有越界的跑次 | 灰白 |
   |---|---|---|---|
   | 原样（V301，带探针） | 7 | 7（每次 1~2 个） | 6 |
   | 原样（不带探针，本会话） | 10 | — | 4 |
   | 把 V301 换成 EDF6 原版 `V601_TANK_AI.SGO` | 3 | 0 | 0 |
   | 炮铰链换成 V601 的轴 | 5 | 5 | 4 |
   | `cannon_slide` 质量 ×0.26 | 3 | 3 | 2 |
   | `cannon_slide` 移出物理世界 | 3 | 3 | 2 |
   | 瞄准参数换成 V601 的 | 3 | 3 | 3 |
   | CAS 加回 `cannon` 静态轨道（本次修复） | 4 | 0 | 0 |
   修复后炮管俯仰跟随瞄准（命令 -0.052 → 姿态 -0.033，-0.094 → -0.063，有缓动滞后），不再整圈转。
7. **41~48 s 的固定时间点**：开场演出约 35 s 结束、世界重建（新的 Umbra Cell，`0x1193400`），坦克开到哨位
   (254, 0, 110) 后开始对远处目标抬炮，随后约一秒爆掉；不是计时器、流送或天气。M001 没有这辆坦克，所以不出现。

## 修复

- `pylib/edf41tank.py`：新增 `CLASS_POSED = {'cannon'}`（601 类就地转的骨骼）；`build` 从 V601 的 CAS 保留 `cannon_slide`
  与 `cannon` 两条轨道，`cas_pose.retarget` 把 `cannon` 的平移改到 V301 自己的骨位（旋转本来就是单位阵）；`check` 要求 CAS
  恰好是这两条、每个片段都有、`cannon` 是该骨的静态静止姿态，并允许 `cannon` 同时有物理回写（V601 亦然）。
- 重新生成 `edf41port/objects/OBJECT/EDF41_V301_RECOIL.CAS` 与 `edf41port/objects.json`（整份 `make_edf41_objects.py`
  重建到临时目录后比较：只有这一个文件和它的 sha 变了）。七个 V301 变体共用这个 CAS。
- 诊断：`src/viewdiag.cpp` 也看 Umbra 的输入，越界的盒子记 `VIEWDIAG umbra`（调用路径、归属对象的类），每局至多 8 条；
  只检查，不改调用。
