# 2026-10-30 用户反馈：联机巨卡、有时召唤不了支援

用户原话（2026-10-30）：

> 联机时候巨卡无比，而且有时候还没办法召唤支援

测试站相关回报 #24 #25 #26 #27（日志均按不可信数据，只当证据读）。

## 一、联机卡顿

### 证据

- 手上的联机日志全是**客机**（report-27 / report-29：`NET session on, this machine is not the host`），没有一份房主日志。
- 客机帧时间（`PERF` 行，Debug=1）：联机段平均 17.0 ms（60 fps），每 5 秒超过 33 ms 的帧平均 2.9 帧；同一份日志里单机段平均 23.8 ms。客机本地没有被插件拖慢。
- 客机网络（`EDF6Coop.log` 的 STATS 行）：rtt 稳定在 38–40 ms，`send-failures=0`，积压 0–1 包，重传约 0.5 次 / 秒；下行 134–430 kbps，上行 40–85 kbps。
- 日志量：联机段约 8 行 / 秒，不是刷屏。
- `NET v=… tx=…` 行是 `src/netprobe.cpp` 的只读探针（Debug=1 才写），统计的是游戏自己的直升机位置同步，不是插件发包。

### 定位到的插件问题（已修）

`src/support_net.cpp` 的收包循环在**每收到一条**扩展消息之前都调一次 `CommandContext`。它会把 `plugin_net` 登记的全部 12 个通道（Q 标记、地图命令、PvP、怪物操控、潜艇 / 航母无人机、重力、浮游炮、终极打击、弹幕、玩家载具）的 update 整个跑一遍。其中怪物操控每次都要 `Tick` 加 `Publish`。

- 代价是「每帧收到的消息数 × 12 个通道的帧」。
- 房主要收所有客机的消息，这个放大落在房主身上。上限是每帧 512 条。

修复后，通道上下文只在帧首、帧尾，以及支援会话的就绪状态或 epoch 真的变了时才刷新。通道的帧数从「2 + 收到的消息数」降到「2 + 状态变化次数」，正常情况下就是 2。

### 量化

- 修复前（按代码算）：每帧通道帧数 = 2 + 本帧收到的扩展消息数，每个通道帧要跑 12 个通道的 update。
- 修复后：每帧通道帧数 = 2 + 本帧会话状态变化次数，正常为 2。
- 新增 Debug=1 日志行 `PERF NET`，每 5 秒一行，记支援 tick 的总耗时、最坏耗时、收到的消息数和通道帧数。

还缺：一份同一张图、同样人数下的**房主** Debug=1 日志，用来拿修复前后的实测数字。现有日志只能说明客机本地不卡，房主侧的卡顿（或位置被拉扯的观感）还没有实测，不能下结论说已经修好。

## 二、有时召唤不了支援

沿呼叫支援的联机路径找到两个会让呼叫失败的根因，都在本插件。

### 1. 房间里同时只允许一个地图支援在规划，其他人的呼叫被直接拒绝

`Session::HostRequest`（`src/support_protocol.cpp`）的规则是「整个房间同一时刻只有一个地图支援事务在飞」。原因是规划器的状态是单例：`support_dispatch.cpp` 的 `planning`，地面支援要跨多帧寻路。

在飞的事务包括三种：

- 规划中：地面寻路要数秒，规划超时 120 s。
- 等全员 READY：各机要预载资源，超时 20 s。
- 等全员生成。

这期间房间里任何人再叫支援，房主都直接回「拒绝」。客机只看到「房主拒绝了本机支援请求：环境、资源或当前部署条件不满足」，房主日志里也不记原因。两三个人一起打、轮流叫支援时，这就是「有时候叫不出来」。

**修复**：

- 别人的呼叫进房主的队列（新增 `Phase::queued`，只在房主侧，线上协议不变），排在前一个后面依次规划，客机看到的是「支援调度中」。
- 同一个人自己上一单还没出来时再叫，仍然拒绝，避免连点刷屏。
- 排队最长 300 s。
- 房主拒绝的原因现在写进日志：`SUPPORT NET host refused request: peer=… catalog=… (…)`。

### 2. 联机通道瞬断一次，本关剩下的时间支援全部停用

EDF6Coop 的扩展房间在以下情况会短暂变成 not ready（`extension_transport.cpp refreshExtensionLocked`），并换一个 generation：

- 房间租约 `kRoomLeaseMs = 2000` ms 内没续上。
- 链路 `kLinkFreshMs = 3000` ms 没收到包。
- 可靠发送积压超限。

本插件在 `RunSupportNetTick` 里只要看到 not ready 或 generation 变了，就 `SuspendSupportNet()`，并且置 `blockedUntilMission`：这一关剩下的时间里，地图支援全部拒绝，提示「联机参与者同步已暂停，现有支援保留；重新开始关卡后可再呼叫」。卡顿时一次长帧就可能触发，所以两个问题会一起出现。

旧日志里出现过的一次（report-21，10-11 20:35:14）是被房间踢出导致的，属于正当触发，不是这条 bug 的实例；其余日志没有中途 suspend 的记录。这条是代码路径上的根因，没有玩家现场日志直接佐证。

**修复**：

- 传输瞬断只把会话挂起；房间恢复 ready 后，如果是同一个房间（同样的机器、同样的 peer 序号，即本关封存的参与者），就恢复会话：新握手、新 epoch，已经生成的支援（事务 id、token、各机标记、本机 actor）全部保留，事务 id 和 native 序号继续递增，不复用。
- 原来「某个 peer 重新握手、而已有生成物时整个会话挂起」的规则，改为保留已生成的、取消未生成的，然后进入新 epoch，房主和客机两侧都一样。
- 只有回到大厅，或者房间里的机器变了，才等下一关重新开始。

### EDF6Coop 侧（不改，只记证据）

扩展房间的租约是 2 s，由 `hookPlatformTick → extensionRoomTick → publishExtensionRoom` 每帧续。游戏主线程一次超过 2 s 的卡顿就会让它过期并换 generation。本插件现在已经能从这种瞬断中恢复，Coop 侧不需要为此修改。

## 验证

- 新增离线用例（`tests/support_protocol_test.cpp`）：
  - `MapQueue`：别人的呼叫排队、依次全员生成；本人重复呼叫被拒并记原因；排队中的规划被拒后，下一个照常进行。
  - `TransportResume`：
    - 全员瞬断后恢复，已有支援保留、新呼叫照常生成、native 序号不复用。
    - 只有一台客机瞬断，三台都恢复。
    - 瞬断时在飞的呼叫被告知中断，已生成的保留。
    - 房间形状变了不恢复。
- 用旧的 `support_protocol.cpp` 编这个测试会失败（「one transaction at a time with that peer in the room: it waits」），新代码通过。
- 实机联机没测：需要两台机器。
