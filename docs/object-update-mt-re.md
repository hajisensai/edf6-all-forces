# 对象更新多线程：骨骼 -> 碰撞代理同步（0x6ED800）

代码：`src/object_update_mt_logic.h`（引擎，纯逻辑）、`src/object_update_mt.cpp`（安装与胶水）。
ini 键 `ObjectUpdateMT`（默认 1）。离线测试：`tests/object_update_mt_test.cpp`，签名审计：`tests/object_update_mt_sig_audit.py`。
以下地址都是 EDF.dll RVA（TimeDateStamp 0x678CCB46），结论以汇编为准。

## 1. 原版

`System::update`（0x1199xxx）的对象循环在 slot5 前后各调一次空锁：开窗是 0x11993CE 处的 `call 0xDAC5B0`，
关窗是 0x119945B 处的 `call 0xDB04B0`，两者都是 `ret 0`，参数是 `[r14+0x68]`。窗内每个 InsectBase / HumanBase
在 slot5 里先调 0x6EDCA0（物理 -> 骨骼），紧接着调 0x6ED800（骨骼 -> 碰撞代理）：

| 调用点 | 字节 | rcx |
|---|---|---|
| 0x4A985C InsectBase | E8 9F 3F 24 00 | rdi+0xB10（前面 0x4A9835 是 0x6EDCA0） |
| 0x57584E HumanBase | E8 AD 7F 17 00 | rsi+0xD90（前面 0x57580D 是 0x6EDCA0） |

0x6ED800 还有约 40 个别的调用者（载具等），这些保持同步，不改。

### 0x6ED800(C)

- 锁：`0xDAC5B0([[C+0xC0]+0x58])`，解锁 0xDB04B0（都是空函数）。
- part 表：基址 `[C+0x78]`，个数 `[C+0x88]`（64 位），步长 0xC0。`+0xA4` 字节为 0 跳过；`+0x9C` 是模式，只处理 1 和 2。
- 合成：bind = `[part+8]`，骨骼 = `[[bind+0x40]]`，行 R0..R3 = 骨骼 +0xB0/+0xC0/+0xD0/+0xE0。
  `row_i = b[4i+1]·R1 + b[4i]·R0`，再 `+ b[4i+2]·R2`，再 `+ b[4i+3]·R3`（标量广播）。之后 0x511C0 把 M 正交化（M 16 字节对齐）。
- 模式 2（刚体部件）：
  - `T = 0x97D9D0(&T, &M)`，写 64 字节（0x6E9130 是同一套合成）。
  - body = `[part+0x50]`。线速度 `0x11B1300(body)`、角速度 `0x11B1060(body, tmp)` 都要满足静止：
    `andnot(image+0x1824540, v) <= image+0x1792EF0`，前三分量都成立。
  - 都静止时，取运动记录 `H+0x20 vt+0x80(id)`（`H = [[body+0x100]+0x58]`）。若 `0x11BAD40(记录, &T)` 为真（姿态没变），跳过这个 part。
  - 否则调 `0x11B0AB0(body, &T, *(float*)(image+0x179F358))`，最后走到 `H+0x18 vt+0x88`。
- 模式 1（节点部件）：`0x109B50(C+0x110, node=[part+0xB0], &M)`，把 M 用 movaps 拷到 node+0x60..+0x9F。
  0x6EDC0C 这个调用被 native_body_math 改成先预取 `[node+0x10]+0xF0/+0x100`。
- 最后 `0x109B80(C+0x110)`，再解锁。

### 0x109B80(K)

- `[K+0x68]`（世界刚体）为 0 时直接返回，K+0xB4 不置位。
- 并集初值：min = image+0x1769300，max = image+0x1769310。节点链表头是 `[K+0xA0]` 这个哨兵，节点之间用 qword +0 相连。
- 对每个 `+0xA0` 字节非 0 的节点：
  - `0x652F0(node+0x40, node+0x20, node+0x60)`，矩阵要 16 字节对齐。
  - `min = minps(min, c-h)`、`max = maxps(max, c+h)`，只写回 xyz。
  - 调 `H+0x18 vt+0x88(id, node+0x60, double[4]{node+0x90}, 1)`，也就是 0xE51570。0xE51651 / 0xE51683 两处补丁在这里面生效。
- 有活动节点时：先 `0x11B0940`（激活）。min 或 max 里有 NaN（0x650E0）时，换成默认值 (−1,−1,−1,1) / (1,1,1,1)。
  再调 `0xDA08E0([K+0x78], &box)`，然后把 box 存到 K+0x80..+0x9F。
- 没有活动节点时调 `0x11B1710`（停用）。
- 最后 K+0xB4 = 1。

## 2. 拆分

纯计算只读 part、bind、骨骼、节点，只写自己的结果区，交给工作线程做：合成、0x511C0、0x97D9D0、0x652F0、并集与 NaN 默认值。

以下部分都有副作用或要读 Havok 的活状态，留在游戏线程上，按登记顺序原样回放：

- 静止判断、0x11BAD40、0x11B0AB0；
- 0x109B50（含预取）；
- 节点 +0x40 写回、vt+0x88；
- 0x11B0940 / 0xDA08E0 / K+0x80 或 0x11B1710；
- K+0xB4、锁 / 解锁。

结果是逐位相同，不只是物理上等价：离线测试比较了整块内存和每一次 Havok 调用的参数。

节点矩阵的来源：如果有 mode-1 part 指向这个节点，用最后一个这样的 part 的 M（原版是后写的覆盖先写的）；
否则用节点自己的 +0x60。计算时世界刚体还没有（K+0x68 为 0）、提交时却有了的话，交给原版 0x109B80 现算。

## 3. 线程与队列

- 线程数 `min(逻辑核数 − 1, 8)`，由插件自己建，不用游戏的 +0x358 队列，也不用 Havok 的线程。
  每个任务登记时记下游戏线程当时的 MXCSR，工作线程跑任务时切换成它。
- 队列是一个 64 位原子量：代号 16 位、已发布 24 位、已认领 24 位。工作线程和游戏线程都用 CAS 认领任务；每次 flush 后代号加一。
- 工作线程在窗口打开、有登记时自旋（先 pause，后 SwitchToThread），窗口关闭后在手动复位事件上等待。
- 每个任务在 `__try` 里跑。出异常时，过滤器写 `EDF6VehicleCrew.objmt.dmp`（带异常现场），这个任务交回游戏线程用原版 0x6ED800 现算，
  并且本次运行之后全部交给原版。part 超过 1024 个、节点超过 1024 个、或结果区不够时，也交回原版。
- 任务表满（1024 个）或结果区用到 75% 时，先做一次 kCapacity flush。

## 4. flush 点

只要有已登记、未提交的任务（cave 先读 `pending`，为 0 就直接执行原字节），并且当前在游戏线程上，就在下列地方把全部任务按登记顺序提交：

| 原因 | 位置 | 条件 |
|---|---|---|
| window | 0x119945B 关窗前 | 总是 |
| ray | 0x11A7EE0 中段 0x11A7F1E（r8 = 射线输入，`[r8+0x20]` = 过滤信息） | 过滤信息可能碰到代理层 |
| box | 0x11A70B0 中段 0x11A70EE（rcx = 收集器，`[rcx+0x10]`） | 同上 |
| body | 0x11A7480 / 0x11A77C0 中段 | 总是（刚体投射，可能就是代理本身） |
| pose | 0x6ED480 / 0x6ED6B0 / 0x6E93B0 中段 | 总是（布娃娃 / 模式切换会直接读写 part） |
| setpos | 0x11B1A00 中段 0x11B1A1D | 总是 |
| delete | 0x118A1B0 中段 0x118A1BF | 总是 |
| recall | 0x6ED800 / 0x6EDCA0 中段 | rcx 是还没提交的容器 |
| dup | 登记 | 同一个容器在同一个窗口里第二次登记 |
| capacity | 登记 | 任务表或结果区快满 |
| plugin | `FlushObjectUpdates()`：enemy_control_native_pose 的 FlushRag 开头 | 总是 |

0x11A7EE0 和 0x118A1B0 的入口字节被别的模块（heli、edf41classes、各个 `*_net`）核对过，所以闸门都放在函数中段。
被挪走的原字节不含 rip 相对寻址，rsp 16 字节对齐，标志位由 pushfq/popfq 保存（0x118A1BF 那条 test 在恢复标志之后执行）。
cave 保存 rcx/rdx/r8-r11 和 xmm0-5。

**过滤层**（0x1061E0）：过滤信息的低 5 位是层号，bit 15–30 是组号。层掩码表是 `[[*(image+0x20B2970)]+8]+0x24` 处的 32 个 uint32，每次开窗读一份。
代理用的层是 5（节点）和 6（mode-2 部件）。只要满足下列任一条件，就判为可能碰到代理：

- 带组号；
- `table[q] & 0x60`；
- `table[5]` 或 `table[6]` 的 bit q 为 1。

读不到这张表时，每次查询都 flush。

## 5. 已知风险（需要实机看）

- **窗口内其他代码读到旧代理**：slot5 循环里，后面的对象如果不经过上面这些闸门，直接读前面对象的代理（K+0x80、节点 +0x40/+0x60、刚体姿态），
  会读到上一帧的值。原版的读法逆向下来只有查询 / 投射 / 布娃娃 / 删除几条路，但没有穷举 slot5 里所有的读者。
- **别的线程上的查询不 flush**：会读到上一帧的代理。原版里跨线程查询本来就和 slot5 没有固定先后。
- **收益有限**：提交阶段的 Havok 调用（vt+0x88 / 0x11B0AB0）仍然是串行的，而且占了大头。离线数据里串行提交和计算的耗时相当。
  实机的 Havok 调用更贵，计算部分占比更低。flush 太频繁也会把并行度打散，`PerfProbe=1` 的 `PERF OBJMT` 行可以看到原因分布。
- **Debug=1 影子核对**：每 64 次登记抽一次，在登记时和提交前各在游戏线程上现算一份，都和工作线程的结果逐位比较；
  每个 part 的 T 还要和原版 0x6E9130 比较。不一致时记 `OBJMT MISMATCH`。
