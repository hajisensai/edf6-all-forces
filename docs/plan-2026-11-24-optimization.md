# 2026-11-24 全面优化计划

维护者原话：

> 「根本性优化游戏，包括性能、可维护性、帧数解锁，让帧数和游戏解耦，还有任何应该去做的优化。应该多线程的多线程，应该并发的并发。联机优化。优化我们mod的旧功能」
> 「不止这点东西吧，能优化的都优化，应该优化的优化」

依据：九路只读审查，原文与逐条证据在 `docs/reviews/2026-11-24-optimization-audit.md`（下文 `fps-3` 之类即该文条目编号）。
已有基础不重做：帧步进真等待（`frame-pacing-re.md`）、Havok 多线程默认开（`havok-mt-re.md`）、TerrainShare 大地图内存（PR #79）、
不限帧率阶段 1（`unlimited-fps-re.md`）、#330 的插件热点修复、CRI loader 池、主插件异步日志。

## 1. 先纠正的几个前提

1. **性能基线已过时。** 47.9 / 108 ms 是 #330 定稿前的数。#330 后 stress:30 = 32.8 ms、stress:100 = 77.4 ms；stress:100 里
   插件 ThinkHook 21.4 ms、`edf::Readable` 8.5 ms、Havok 约 9 ms，**原版剩约 40 ms 从未按阶段拆过**。PERF 行按帧计时，但 stress 下
   一帧要补 3 步（`0x11A2F76` 夹到 ≤3），「ms/帧」会误导方向（cpu-1）。
2. **GPU 不是瓶颈。** stress 实测 GPU 3D 3–17%，重场景卡在游戏线程。D3D11 deferred context 并行提交不做（gpu-9）。
3. **`unlimited-fps-re.md` 有三处要改**（fps 摘要、latency-4）：滚轮 / 鼠标要在动作封装层累加（输入晚一帧才被步进读到）；
   SyncInterval 不是游戏设置，原版恒为 1、仅追帧后 8 帧为 0；镜头投影调用点 `0x1197B50` 已被 `scope_lens` 占用，插值并进它的钩子。
4. **`frame-pacing-re.md:99` 说渲染栅栏「真等待」不对**：`0x111CC20` 是 `WaitForSingleObject(h,0)+Sleep(0)` 忙等（gpu-1）。
5. **不限帧率不需要升联机协议**：EDF6Coop 的每帧工作都挂在 EOS tick（只经 `0x7056AE`），n = 0 帧守住即与原版同节奏（fps-2）。

## 2. 不做的（有证据的否决）

- 并行化原版对象的 Think / Update 虚函数循环（cpu-9）：竞态与联机分歧风险，收益不可证。
- 立即上下文保留单一提交线程（gpu-9）。渲染录制与模拟的独立推进见下方线程边界。
- 改 ResourceManager 固定 4 槽（hitch-11）：除非加载基线证明是 CPU 瓶颈。
- 模拟改成按真实时间变步长（`unlimited-fps-re.md` §0.3）。

## 3. 分线与排期

七条线。同一批里各线改的文件不重叠，可并行；每条线自成分支和 PR。凡标 G 的都按实机铁律排队拿游戏验收。

读法和后续取舍：

1. **重场景纯粹卡在游戏线程的步进。**
   - stress:30 / 100 每帧都补满 3 步，模拟只剩 40 / 15 步每秒，即原速的 66% / 25%。
   - 游戏线程占 86–87% 核；GPU 3D 只有 5–9%（轻场景 17–24%）。
   - 绘制录制每帧 3.4 / 8.7 ms，只占帧时间的 4–5%。
   - E 线（插件每帧开销）和原版 object_update / ai_update 是主战场。
2. **n = 0 帧地板低（cpu-11）。** 轻场景 2–3.6 ms（不含步进和 tick 等待），其中 1.4–3.3 ms 是栅栏忙等 `0x111CC20`。
   B 线的不限帧率可行，但应先把这个忙等改成真正的等待，否则高帧率时它会吃满一个核。
3. **输入到画面的延迟。** 60 fps 下画面用的是两帧前的采样，约 36–40 ms。stress:30 涨到 226 ms，stress:100 涨到
   613 ms，最差超过 1 s。latency 线的收益在轻场景；重场景只能靠减步进时间。
4. **GPU 提交量（gpu-2）。** pass 3 和 mesh draw 随单位数近线性增长：stress:100 每帧约 1.5 万次 mesh draw，但 GPU 只占
   5%，不是瓶颈，G 线优先级低。
5. **还没测到的：**
   - Umbra resolve 调用点 `0x11B6B1D` 在这些场景里计时恒为 0：resolve 不在这条路径上。umbra_sandlot 的栈叶出现在另一条
     线程上，要另找。
   - 联机（net-1）和 PresentMon（latency-2）这一轮没有数据：离线跑，PresentMon 需要管理员权限。工具已就绪：
     `--presentmon`，以及 coop.log 自动保存。

### B. 呈现链与不限帧率（第一批起，顺序做）

1. 小补丁先发：gpu-1 渲染栅栏改真等待；latency-1 `SetMaximumFrameLatency(1)`；文档更正（§1.3、§1.4）。
2. 不限帧率阶段 2（Debug 开关下）：fps-1 帧门小桩、fps-2 节奏守卫逐个改调用（含 `0x7056AE` 守住 Coop）、fps-3 输入在封装层保留、
   fps-4 插件接管 SyncInterval。同批并入 latency-3（封装更新挪到 System::Update 之前，少一个 tick 延迟）——它和 fps-3 挂同一对钩子。
3. 阶段 3：fps-5 抓镜头步进结果、fps-6 镜头插值并进 scope_lens、fps-7 玩家 / 载具根变换插值、fps-8 插件镜头切换断点 API、fps-9。
   fps-6 与 fps-7 必须同时对用户开放。
4. latency-5 / gpu-3 交换链翻转模型 + ALLOW_TEARING（不限帧率真正上屏的前提），latency-7 tick 相位锁 vblank，latency-8 Raw Input。
5. 阶段 4 / 5（全部骨骼、植被风、着色器时间、特效）与 fps-10 联机实测。

### C. 联机（第一批起；Coop 仓库部分在 Coop 自己的 worktree）

- 先修：net-2 `extensionFault_` 粘滞（一次积压后本关插件联机全失效，10-30 反馈未修的那条根因）；net-3 NetId 解析每帧缓存；
  net-4 节奏改用 QPC / tick 而非 `GetTickCount64`；net-7 / net-8 收包循环批量加锁、通道更新去重。
  - 2026-11-24 已做（不升线协议；Coop 分支 `claude/1124-ext-fault-recover`，AF 分支 `claude/opt-net-6447d4`）：
    - net-2：改前，任一条链路积压超 1 MiB / 8192 包或收件箱超 4096 条就把 `extensionFault_` 置死，本房间余下时间插件联机全断。
      改后，溢出等同一次就绪闪断：清收件箱、换 generation（AF 照常挂起 → 恢复，房主恢复开新 epoch，各客人通道经 RoomWatch 重置）；
      积压期间保持未就绪，各参与链路降到 ≤512 KiB / ≤4096 包后自动恢复，不再锁死。能力位 bit 2 声明此契约。
    - net-7：改前，每帧最多 512 次 `extensionPoll`，每次拿 DirectNet 的 `mu_` 并 refresh 一次；AF 每条清零 1 KB、strcmp 查对端。
      改后，新可选导出 `EDF6CoopPollExtensionBatch`（能力位 bit 3）：一次加锁取 64 条，发送者直接给 `api.peer` 下标；
      AF 一帧通常一次加锁（满 64 条才再取）。
    - net-8：改前，收包前、收包后各跑一遍全部通道 update。改后，收包前那遍只在房间（就绪 / epoch / 名册 / 本机身份）变了时跑，
      平常每帧一遍。未做：怪物操控每条消息仍 Publish 一次、`EnemyControlNetworkFrame` 与 update 的 Tick 仍各一次（要把夹具里
      「收包即可读状态」的断言改成按帧读，单独做）。
    - net-3：改前，每次 NetId 引用解析都完整遍历世界（0x5E0C80）。改后，同一逻辑帧内第一次遍历顺手建 NetId 索引表（开放寻址，
      带帧戳），之后命中直接用，并按 StillNetRef 同样的条件复核（仍在场、同一对象、NetId 未变、存活条件）；未命中仍遍历，
      所以本帧新建的对象照样找得到。
    - net-4：改前，怪物操控姿态 / 输入按 `GetTickCount64` 的 33 ms、重力按 50 / 100 ms 限速；15.6 ms 步长的时钟把两帧读成
      31 或 32 ms，实际约 20 Hz 且不均匀。改后，按逻辑帧（`GameFrame`，System+0xCE0）：输入 / 姿态每 2 帧（30 Hz），
      重力持握 3 帧、飞行 6 帧；超时仍按毫秒。
    - 房间门槛：AF 要求 EDF6Coop 声明能力位 2、3 并导出批量收包，否则拒绝建房 / 进房并提示升级 EDF6Coop。

#### 原版骨架子树更新与战场采样有效性

实机栈中的 `0x1100010` 是士兵、巨蚁等共同涉及的骨架子树更新。它按记录顺序把 `local × parent.world` 写入具有本地标志的骨架记录。新内核一次载入并合成两行，保留标志判断、父子写回顺序和原版加法顺序。仅在 CPU 与 Windows 已启用 AVX 寄存器状态且原生签名匹配时重定向三个原版调用点，其余机器继续使用原版。AVX 启用检测依照 [Intel SDM §14.3](https://cdrdv2-public.intel.com/843827/253665-sdm-vol-1-dec-24.pdf)。

离线用私有映射的真实 EDF.dll 比对三个重定向入口，3,600 次子树更新的整个骨架记录逐字节一致。192 骨骼夹具运行 100,000 次的中位耗时从 53.63 降至 31.04 ms。这个样本衡量子树矩阵合成，实机整帧收益另行采样。

页缓存和寻路新版的原实机复测中，`stress:10` 有有效帧区间；`stress:30` 在 14:53:42 报告任务进入，但敌群在 14:54:22 之后才出现，15 秒清洁窗口已经结束。`perfrun.py` 为预期有敌群的场景把暖机起点绑定到本关新记录中的存活敌人数。若测量窗口内缺少对象计数或没有敌人，记录失败并按原流程还原游戏文件。无敌群计划和显式关闭对象遥测的运行沿用入关起点。

`9edc6242` 的单场 `stress:30` 实机验证在首条非空敌群记录后暖机 15 秒。DLL SHA-256 前缀 `2fcf053092fa0c17`，启动日志确认 `BONES ... 3/3`，游戏线程栈采到 `ApplyAvx`。12 秒清洁窗口的对象采样为 1,546 敌、662 友；63 个有效 PERF 帧平均 79.80 ms，其中步进 73.29 ms。原版对象更新约 32.64 ms/帧，Havok 步进约 12.96 ms/帧，仍是优先调查对象。该场的存活规模不同于先前基线，数值仅用于定位热点及验证新版运行。测试退出后原 DLL 和配置逐文件还原，游戏租约释放。

同配置 `stress:30` A/B 使用归档的优化前后主插件和同一份 AutoTurret，敌群就绪后暖机 15 秒，再测 15 秒。A/B 均有 662 友军，敌军均值为 1,726 / 1,877，平均帧耗时为 98.25 / 81.13 ms，帧内步数均为 3。两轮均成功退出并还原文件。单轮对照且双方存活规模仍不同，帧耗时差只能作为收益方向的证据。

挂接碰撞体的另两个数学热点改用打包 SIMD。仅重定向已核对输入输出互不覆盖的 `0x109C09` 包围盒变换，以及 `0x6ED9EB` 的坐标系正交化。包围盒计算保持原加法顺序；正交化保留平移和各行第四分量，长度平方溢出或无序时由原版处理。私有映射的 EDF.dll 对照中，每个调用点的 20,000 组输出逐字节一致，覆盖退化值与启用近零清理时的运算。50 万次包围盒变换从 1.10 降至 0.97 ms，50 万次正交化从 20.75 降至 6.23 ms。合成内核结果独立于上一组实机 A/B。

### 渲染与模拟的线程边界

目标是游戏线程持续推进固定步长模拟，渲染线程只消费已提交的场景数据并独立呈现。同一帧的相机、姿态、可见集和资源引用需要成套交接。

1. 插件第一人称相机状态和提交历史已改用 `src/render_snapshot.h`。生产者先在私有暂存区构建，渲染和激光读者各自持有已提交的副本。只有读到同一版本的原子载荷才接受本次发布。绘制读者无需等下一次模拟步进。
2. 原版帧的命令回放和 Present 已在线程入口 `0x111B8E0` 上执行。游戏线程在 `0x1198FA4` 调 `0x11978D0` 录制，之后才进入模拟步进，帧末通过 `0x111CC20` 同步渲染命令。这里需要拆的是录制对游戏对象的依赖和帧间资源寿命。
3. `RenderPoseSnapshots=1` 开启原生姿态快照实验。录制期间登记 `0x1100F10` 刷新的骨架实例，在首个投影的其他插件回调之后封存矩阵。开始与退还标记占用原版渲染队列的单个单元，渲染线程按同一 FIFO 选择和退还快照。
   - 蒙皮 `0x11009A0`、刚体子网格 `0x1103DA0` 都从绘制参数 `list+8` 取同一份矩阵，保留原版调用的骨架、逆绑定与 GPU 资源。第一人称为已覆盖实例在绘制私有内存里算手臂、武器和仪表变换，嵌套绘制按实例选覆盖。
   - 捕获对象只包含录制线程在首投影之前刷新过的骨架。其他线程刷新、录制外的绘制、地址重用、资源失效、渲染回调自己刷新姿态以及三个在途槽耗尽都有独立的原版路径。每槽最多 32 MiB 姿态数据，槽保留高水位供后续帧复用。发布默认保持关闭。
   - 高刷根变换先对已登记骨架保存原始矩阵和变换。渲染线程首读时在私有副本上应用一次，不改原版姿态，也没有该骨架的帧末还原。未能登记的骨架保留原路径。
   - 匹配原版上传大小的蒙皮缓冲随帧持有 D3D11 引用，同时复制逆绑定。渲染线程首个 pass 按原版三列布局计算调色板，其余 pass 复用，最后一条回放标记释放引用。临时第一人称覆盖以及缓冲重新绑定仍用原版上传逻辑。每槽最多额外保留 14 MiB 逆绑定和三列调色板。
   - 帧槽扩容只搬运当前录制已写入的矩阵与逆绑定前缀，空容量由捕获或打包时写入，上一帧数据无需搬运。只给确实插值的骨架分配变换矩阵。原生骨架标识在首次投影前更换时丢弃旧变换，封存新数组。离线基准每帧 3,072 个 64 骨骼实例，12 个冷帧槽的耗时中位数从 133.23 降至 85.44 ms，已预热槽复用从 3.83 降至 3.78 ms。基准使用模拟缓冲，覆盖 CPU 姿态准备、回放读取与帧槽扩容。
   - 离线 `render_pose` 覆盖原生队列标记、矩阵变换、引用回收和两类消费者，软件 D3D 验证了实际常量缓冲上传。`frame_rate_sigs` 静态核对 EDF.dll 字节、矩阵读写地址和 FIFO 回放。
   - 回放一次按骨架标识查找帧内姿态与调色板。D3D 缓冲重绑时沿用冻结的姿态并走原版调色板计算。原版 LOD 入口 `0x1104100` 会先上传再进入网格函数 `0x1103DA0`。在帧回放中，网格函数判定阴影剔除或对应网格表为空时，直接经网格入口完成原版状态处理，省去一次调色板计算或上传。软件 D3D 读回确认空 pass 的缓冲内容不变、有效 pass 上传录制姿态。签名审计核对两个原生分支及调用链。
     合成基准的 4,194,304 次热缓存姿态与调色板查询中，五次交错测量的中位耗时从 36.07 降至 26.43 ms。该数值是 CPU 查找耗时，空 pass 在实机中占多少仍需采样。
4. 可见性和资源寿命仍与原生场景耦合。录制内的对象回调会通过 `0x11B30C0` 更新 Umbra 包围盒，主视口存在 `0x1197F93 → 0x11B6770` 的队列路径，另一条 `0x1198656 → 0x11B6AA0` 可先在录制端调用 `0x11B6B1D` 的可见性解析。核对当前 Umbra DLL 后，`resolveVisibility` 会在调用线程提交请求并通过信号量唤醒 Umbra 自己的工作线程。包围盒变换与查询要保持这条内部队列的先后顺序，单独推迟包围盒写入会改变查询读取的场景。场景切换、分屏、镜中镜和交换链重建还要和资源耗尽、模型释放的时序一并处理。
5. `RenderRecordThread=1` 在插件加载时安装完整原版录制入口跳板。战斗内经 `0x1198FA4` 进入的插件回调和原版 `0x11978D0`，以及另外四处加载 / 菜单调用的原版函数体，都交给同一条独立录制线程。只设置这一项即可同时启用原生姿态快照。
   - 录制线程按原顺序执行对象回调、可见性提交和原版命令录制。每个调用同步移交场景访问权，保持原版参数、结果和异常语义，模拟收到完成信号后才继续。原版 GPU 回放线程仍按 FIFO 独立消费，可以与后续模拟重叠。
   - 录制线程迁移与录制、模拟同时修改场景是两件事。原版 `0x11978D0` 仍经对象虚表执行活动场景回调。还需冻结所有这类读写及模型、材质、粒子资源，才能取消录制完成等待与原版帧末资源栅栏。
   - `render_record` 离线执行真实的 x64 入口跳板和专用工作线程，覆盖并发调用、重入、回调顺序、异常及启动失败回退。`frame_rate_sigs` 核对 Steam EDF.dll 的五个直接调用点及回到模拟的位置。这个实验默认关闭，本轮未进游戏测画面与帧时间。

### G. 渲染小项（第二批，按 A 的 gpu-2 数据）

gpu-4 混合显卡笔记本跑核显（先核实插件能否影响 exe 导出 / 适配器选择）；gpu-5 Umbra GetData 不带 DONOTFLUSH；gpu-6 蒙皮调色板每 pass 重算；
gpu-7 小物体按屏幕尺寸剔除距离；gpu-8 阴影低一级 LOD（低端机选项）；gpu-10 Umbra resolveVisibility 只量。

#### G 的结论（2026-11-24，分支 `claude/opt-gpu-1124`）：gpu-4 / 5 / 6 / 7 都不改代码

**共同前提：渲染线程不在关键路径上（A 基线，`tmp/perf/base-*`）。**

- 渲染线程只占一个核的 10.9%（M001）、17.3%（RM015）、19.5%（stress:30）、16.5%（stress:100），而且其中 25–63% 的
  样本停在空闲等待（ntdll `0x51e90`，栈底是渲染线程入口 `0x111B8E0`）。
- 游戏线程在 stress 场景等渲染栅栏的时间：
  - stress:30 每帧 75.3 ms 中只有 1.56 ms（2.1%）；
  - stress:100 每帧 204 ms 中只有 2.74 ms（1.3%）。
  - 渲染线程省下的任何时间，最多也只能从这一段里扣，所以重场景的帧率收益上限就是这 1–2%。
- 轻场景已经锁在 60 fps，被 tick / vsync 卡住，渲染线程省时间不会变成帧率。
- 只有 B 线的不限帧率做完、轻场景的帧地板变成 n = 0 的 2.2–3.6 ms 时，渲染线程才可能上关键路径。
  - 那时地板里的 1.4–3.3 ms 也是栅栏忙等（gpu-1，B 线处理），不在 G 线。

**gpu-5（遮挡查询 GetData 不带 DONOTFLUSH）：不做。**

新探针 PERF GPU 直接数了 `0x1631790` 的每次调用（锚点见 `docs/perf-probe-re.md` §2）：

| 场景 | 每帧读取 | 未就绪 | 带等待 | 合计 ms/帧 | 单次最差 ms | 栈份额（渲染线程内，A 基线） |
|---|---|---|---|---|---|---|
| M001 | 10.6 | 0.0 | 10.5 | 0.073 | 1.63 | 1.3% |
| RM015 | 未实测 | | | | | 5.5% |
| stress:30 | 未实测 | | | | | 3.1% |
| stress:100 | 未实测 | | | | | 1.7% |

- 结果**从没出现未就绪**：DONOTFLUSH 只影响未就绪时的 Flush，而这条路上根本不触发 Flush。改了也省不下东西。
- 几乎每次都带等待，但等待从不真的发生，因为结果总是已经就绪。审计担心的「自旋最长 1 s」在这些场景里没有出现。
- RM015 和 stress 场景按原则没有再开游戏（M001 已是一次实机），原因：
  - A 基线里 `0x1631790` 在 stress 渲染线程内只占 1.7–3.1%，乘上渲染线程本身 16–20% 的核占用，不到 0.6% 核；
  - 渲染线程又不在关键路径上。
- 何时值得重做：
  - PERF GPU 里「not in yet」或「waiting」的耗时明显上升时，比如某类场景每帧超过 0.5 ms，或单次最差超过一帧；
  - 并且渲染线程已在关键路径上（不限帧率）。
  - 那时先查是哪类查询要求同步，从源头改，不加超时。

**gpu-6（蒙皮调色板每 pass 重算）：不做。**

- M001 每帧 92 次，合计 0.08 ms/帧。
- 在 A 基线的 stress:30 里，LOD 绘制 `0x1104100`（含调色板）只占渲染线程样本的约 10.5%，约合 2% 核，而且不在关键路径上。
- 缓存方案要把第一人称按 pass 改姿态的逻辑算进缓存键里（fp-render-re.md §2、§17），风险中等，换不来可见收益。
- 何时值得做：不限帧率时，同屏蒙皮单位多的场景里渲染线程忙到接近满核，PERF GPU 的 `skin palettes` ms 占帧地板的 10% 以上。

**gpu-7（小物体按屏幕尺寸剔除）：不做。**

- 它省的是渲染线程和 GPU。GPU 3D 在 stress 只有 5–9%，渲染线程不在关键路径上，所以现在剔除碎片换不来帧率。
- 它还会带来可见变化：远处小物体提前消失，要按 view-distance-re.md 回归远景。
- 何时值得做：
  - GPU 成为瓶颈时，比如低端显卡、4K 不限帧率时 GPU 3D 接近 100%；
  - 或者 PERF RENDER 的 pass 3 / mesh draw 在实际关卡里以碎片和道具为主时。
  - 那时再按 pass 计数定系数 k，并截图对比远景。

**gpu-4（混合显卡笔记本跑核显）：插件改不了，不做。**

- 插件确实在建设备前加载（aiworld-re.md:60、cri-fs-loaders-re.md:61），时机来得及，但有两条路都走不通。
- 一，导出符号：
  - NvOptimusEnablement / AmdPowerXpressRequestHighPerformance 按 NVIDIA / AMD 的说明只认**进程 exe** 的导出，
    DLL 里导出不起作用。
  - EDF6.exe 没有导出表。
  - 这一条依据的是厂商文档和社区经验，本机没有混合显卡，无法实测。
- 二，改调用点 `0x111B595`，用 EnumAdapterByGpuPreference(HIGH_PERFORMANCE) 选适配器：
  - 游戏把设备所在的适配器（cmdctx+0xF0，`0x111B65E` 取得）也当作输出所在的适配器。`0x111A64F` 在它上面
    EnumOutputs 建显示模式列表，失败就退到 1280x720 加空列表（`0x111A98D`）。另外还有 5 处用到 +0xF0（perf-probe-re.md §2.1）。
  - muxless Optimus 笔记本的独显通常没有输出（推测，未在实机验证）。强制选独显会弄坏模式列表和全屏。
  - 要做对，就得把这 6 处输出相关的用法都改到「有输出的那块适配器」上。这是结构性改动，而且本机只有 RTX 5090、没有核显，没法验收。
- 三，没有受影响的证据：
  - 测试站 51 份反馈 / 日志（只当证据读）里，能看到渲染适配器的是 ReShade 日志：「Running on NVIDIA GeForce GTX 1050」
    （同一用户的网卡是 Intel Wi-Fi，像笔记本，已经跑在独显上）和 RTX 4060。
  - 没有任何一份显示 Intel / AMD 核显在渲染。
- 可行的替代（未做，属于文档）：有用户反馈笔记本帧率异常低时，让他在 Windows「图形设置」里把 EDF6.exe 设成「高性能」。
  这是系统级设置，作用于 exe，不需要插件。
- 何时重做：测试站出现核显渲染的日志，并且有混合显卡机器能验收。届时连同 +0xF0 的 6 处输出用法一起改。

### Havok 运动属性 ID 容量边界

未修复版的 stress:100 诊断记录到 69,963 个活跃属性、70,656 项容量。栈在原版刚体创建和扩容回调中命中该路径。原版分配器使用 24 位空闲槽索引，随后将索引截为 16 位写入物理属性。私有映射中，索引 65,536 返回 0 并覆盖了槽位 0。把槽位单纯当成失败值传回也不够，xgs 刚体和两个原生控制器构造点随后直接使用返回的 ID。

运动属性查重、常规扩容和空闲链摘取现在共用 65,535 项的界限。有效 ID 为 0–65,534，0xFFFF 保持原版失败哨兵。只在三个必须取得有效 ID 的构造调用点处理满库。优先使用物理属性完全一致的内建预设，找不到时按请求选择静止、零重力或普通动力预设。满库之后的新对象可能采用预设的物理参数。原生控制器的释放路径保护这些共用预设，普通动态槽位仍能释放、再分配。

私有 EDF.dll 夹具逐项验证了 65,534 至 65,537 的分配边界、原有槽位未被覆盖、满库扩容拒绝、三类预设回退及释放后重用。15 项定向 CTest 通过。

预设包装的最后一个拥有者销毁后，原生 xgs 弱缓存仍可能保留旧条目。遇到失效的预设弱引用时，新路径转入既有包装构造分支。指令夹具覆盖空控制块、引用计数已经归零和仍存活的预设包装，也复核普通 ID 的原路径。

修复后的计数场在容量和活跃数均为 65,535、最大槽位为 65,534、空闲链为空时，记录了 36,864 次构造调用。15,295 次返回预设，全部返回值可表示，空闲链未出现越界槽位。该场用于核对边界和回退逻辑。

### 满库时跳过无效扩容通知

在 stress:100 的独立构造计数场，清洁窗口收集 512 个抽样。其中 239 个要求独占的条目都来自创建时未加入世界的刚体，两批的运动属性内容各只有三种。满库且空闲链为空的 375 个抽样均只有一个监听器，回调为原版 0x11AE920。该回调唯一的工作是请求把库增加 1,024 项，达到 16 位容量后一定失败。

### 当前重场景的剩余游戏线程开销

固定刚体区域复用通过回归后的构建 32407259c23062d1，在 stress:30 的清洁窗口平均 1,548 敌、662 友，162 个有效帧平均 92.75 ms。游戏线程的采样分摊估计为原版对象更新 33.40 ms/帧、对象预更新 20.79 ms/帧、AI 更新 14.62 ms/帧、Havok 步进 13.33 ms/帧。蚂蚁的对象更新命中最多的一段经过动画骨架向碰撞代理提交姿态。同一构建的这场用于定位剩余开销。游戏正常退出，DLL 和配置逐字节恢复。

### 原版选敌先比较已持有目标的候选身份

默认选敌回调在 TeamManager 的临界区内运行。0x54A3B0 的函数指针只在原版最近目标回调表中出现。普通对象更新在选敌返回后经 0x54C130 写当前目标，插件显式设置用 0x364EB0。快速路径在每个候选处重新读取当前目标地址。地址相等时仍让原版 0x30C0F0 验证弱引用，保留过期和地址复用的处理。地址不等时跳过原生解析。候选顺序、加权、保留分数、首次相同分数胜出的规则继续由原版执行。安装时核对候选回调和弱引用解析函数的完整指令指纹。

私有原版映射用 256 组输入对比候选指针与分数位模式，覆盖有无保留目标、空控制块、过期引用、状态过滤、加权、异常坐标和并列。17 项定向回归通过。固定输入里每 64 个候选包含 1 个相同地址，50 万次检查由 5.94 降到 2.33 ms。每种取五轮交替计时的中位数。

stress:30 影子场仍执行每次原生解析，按每 31 次抽样一次。在 22 秒清洁窗口闭合的 139 批共 284,672 次抽样中，284,615 次可跳过。原版实际确认的 57 次命中全部通过地址判断。正式 DLL ee22b0de1a2172a8 启用优化并完成同一场景，平均 1,528 敌、662 友、整帧 91.65 ms。影子场含计数探针且平均 1,663 敌，因此用于验证判定等价和覆盖率。两场均正常退出，原游戏文件逐字节恢复。

原版仍逐项遍历敌对登记对象。该回调的 SIMD 指令追踪也确认，平方之前的多次重排只是保留 XYZ 差并替换第四通道。进一步减少单项开销时仍需保持原版浮点运算顺序和第四通道。

### 压缩原版选敌的候选评分路径

原版的向量重排可以用两条 SSE2 指令得到相同的 XYZ 差和原版第四通道。平方、按原顺序加总、可选权重与严格分数比较沿用原版运算。普通正距离直达平方根。正负零、无序与原版的平方根后备分支仍保留。上一轮的已持有目标地址比较并入候选循环，地址相等时仍调用原版弱引用解析。保留原版保存寄存器和退栈位置，两处原版调用都在同一段展开范围内。安装检查完整函数指纹和覆盖字节。

原版敌对队伍枚举仍逐项走树。它的每候选分派还会先调用固定转发器 0x5E2CC0，转发器才把原访客交给真正的回调。已确认两层转发只改 RCX 和 RAX，候选 RDX 与原访客动态分派相同。可以进一步实测直接分派，并保留原调用返回地址。

### 原版敌对枚举直接调用访客回调

原版敌对队伍遍历先调用固定转发器。转发器仅加载原访客、读取其虚表并跳到回调。现由原枚举函数直接完成这些操作。调用指令和返回地址仍在原位置。每个候选继续读取访客当时的虚表。安装检查枚举函数指纹、转发器指令和实际虚表槽。

私有 EDF.dll 夹具执行完整原版枚举。前后得到相同的遍历顺序、敌对关系过滤、死亡及 NoTarget 过滤结果。回调执行时持有原队伍锁，收到的候选与返回地址相同，首次回调切换虚表后下一候选进入新回调。17 项定向 CTest 全过。

5 次对照每种版本各运行 2,095,104 次候选回调，每次取 7 对交替计时的中位数。以线程执行周期计，旧版每个候选 16.12–17.01 周期，新版 15.29–15.67 周期，组内降幅约 4%–9%。墙钟时间两边有快有慢。正式 DLL dc815ad6ea920d8c 在 stress:100 启用直接派发，代码所有权无冲突。平均 1,416 敌、2,132 友，整帧平均 209.24 ms。15 秒栈采样里，15 条栈命中候选回调的原返回地址。游戏正常退出，原文件逐字节恢复。
