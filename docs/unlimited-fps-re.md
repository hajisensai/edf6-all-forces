# 不限帧率：60 帧锁、按帧推进的时钟与渲染 / 模拟解耦方案

2026-11-10。对象是 Steam 版 EDF.dll（`0x678CCB46`）。维护者原话与来源见 `docs/feedback-2026-11-10-unlimited-fps.md`。
相关：`docs/frame-pacing-re.md`（tick 时钟 `0x11DAE60`、主循环按帧执行的点）、`docs/camera-re.md`、`docs/fp-render-re.md`、`docs/hud-re.md` §10。

证据级别：**H** = 本次或之前用 `tools/edfre.py` 只读 EDF.dll 反汇编逐条核实；**M** = 静态读到了主要路径、个别环节没逐层核实；
**L** = 只有第三方研究包（不可信数据）的说法或推断，未核实。

## 0. 结论

1. EDF6 的 60 帧锁**不是垂直同步**，是主循环的 tick 门：`0x11DAE60` 按 1/59.94 s 数「距上个边界过了几个整 tick」（n），
   n = 0 就 `Sleep(1)` 再数（本插件已把这个等待换成 `TickWait`，见 `frame-pacing-re.md`）。整个模拟按 tick 步进：
   `System::Update` 先渲染、再把场景步进 n 次（H）。
2. 只拿掉等待（社区流传的两字节补丁，就是把 `0x11A2F65` 的 `Sleep` 与 `0x11A2F74` 的 `je` NOP 掉）后，主循环会跑 n = 0 的帧：
   模拟**不会**变快（步进只按 tick），但这些帧画的是同一个状态（重复帧，看起来仍是 60 帧），并且下面 §2 那些「按帧」而不是
   「按 tick」跑的点会出错：植被风加速、滚轮与按键边沿丢失、鼠标位移丢失、输入抑制倒数加快、网络更新变频繁。
3. 把模拟改成按真实时间变步长（「所有按帧推进的时钟改按时间」）**不可行**：游戏数据本身以帧为单位——武器 SGO 的装填 / 连射 /
   弹速（米/帧，`carrier-laser-re.md`）、AI 与动作的计时、`System+0xCE4` 每 tick 加 1/60、动作重复倒数按 n 减（§2.4），
   Havok 世界按固定步长步进，联机两端按 tick 对齐。要改就得把数千处常量与所有对象的更新函数一起改，且无法证明与原版一致。
4. 正确的根因方案：**模拟留在 59.94 Hz，多出来的帧只做呈现**，在「上一步」与「这一步」两个模拟状态之间按相位插值渲染侧的数据
   （镜头、角色与载具的骨骼、粒子 / 拖尾 / 弹、植被风、着色器时间），并把 §2 那些按帧跑的点改回按 tick 节奏。显示时间比模拟晚一个
   tick（16.7 ms），换来连续的画面。这也是第三方研究包（§3）选的方向；它做了几个月，**只有镜头一项有实机遥测**，整体未验收。
5. 本 PR 是阶段 1：纯逻辑（呈现槽、渲染相位、刚体插值、输入边沿保留）+ 离线检查 + ini `FrameRateCap`（只读取，**未接入游戏**）。
   游戏侧的接入（阶段 2 起）每一步都必须实机验收，见 §5、§7。

## 1. 主循环与 System::Update（H）

```
0x11A2EDA: lea ebp,[rsi+3]                     ; ebp = 3（每帧最多补 3 个 tick）
0x11A2F4F: call 0x11DAE60 ; 0x11A2F54: mov ebx,eax ; test eax,eax ; jne 0x11A2F76
0x11A2F60: mov ecx,1 ; 0x11A2F65: call [Sleep]（插件：TickWait）
0x11A2F6B: call 0x11DAE60 ; 0x11A2F70: mov ebx,eax ; test eax,eax ; 0x11A2F74: je 0x11A2F60
0x11A2F76: cmp ebx,ebp ; cmova ebx,ebp         ; n = min(n, 3)
0x11A2F83: call 0x66D00                         ; dt = 秒表（实际帧间隔），1/dt 存为帧率显示
0x11A2FAC: [rdi+9] 置位时清掉并令 dt = 0、n = 0（原版自己的 0 tick 帧，谁置位未查）
0x11A2FCF: [rsp+0xB8] = {dt, n}
0x11A2FF3: call 0x1182A10                       ; 输入对象 [0x20B2888] 的回调（鼠标位移、滚轮取走在这里，§2.4）
0x11A3006: call [rax+8]                         ; Application::Update(0x705530)({dt, n})
0x11A305A: call 0x111CC20                       ; 等渲染线程栅栏（原版零超时轮询 + Sleep(0) 忙等，插件 FenceWait 改成真等待，frame-pacing-re.md）
0x11A306B..0x11A3079: [rdi+0xC] 每帧减 1（负数夹回 0）；n > 1（追帧）时置 8
0x11A3095: cmp [rdi+0xC],0 ; sete dl ; 0x11A309B: call 0x111D890   ; 把 {渲染器, dl} 录进渲染环
                                                ; 渲染线程 0x1118AF0 取出，0x1118B45 Present(SyncInterval = dl, 0)（交换链 = 渲染器 +0x90，vtbl +0x40）
```

**SyncInterval（H，2026-11-24 更正）**：游戏没有垂直同步设置。`0x111D890` 的唯一调用者是 `0x11A309B`，参数就是上面的
`sete dl`：平时恒为 1（等垂直同步），只有追帧（n > 1）之后的 8 帧为 0。这 8 帧按**渲染帧**数，不按 tick；帧门开着时
144 fps 下只剩约 55 ms。旧版 §4.1 写的「由游戏设置决定、来源未查（M）」不对。

`System::Update`（`0x1198DA0`，`0x705715` 调，`r12d = n`）：

```
0x1198E0A..0x1198E33: 未暂停时 System+0xCE4 += n * (1/60)，再 0x112BAA0 把它发给 XGL 着色器时间
0x1198E3E / 0x1198ED0: 非任务状态（加载等）各自按 n 循环
0x1198FA4: call 0x11978D0                       ; 渲染：0x1197B50 → 0x118DFF0（读镜头 +0x220 建视锥、交 Umbra）→ 绘制
0x1198FB0: test r12d,r12d ; je 0x1199734        ; n = 0：整段跳过
0x1198FD0..0x119972E: 每个 tick 一轮：场景步进计数 +0xCE0 += 1（插件的 GameFrame）、所有对象更新、
                      0x11995A6 call 0x118DF40（视口镜头第 4 槽步进：CharacterGhostCamera 0xF86A0 写 cam+0x220）
```

所以：**一帧的渲染在它的步进之前**，画的是上一帧最后一步之后的状态；镜头只在步进里动（H）。

每帧的输入顺序（H，2026-11-24 核实）：`0x11A2FF3` 先采原始输入（回调 `0x1188270`：鼠标 `0x11831F0`、滚轮 `0x11832D0`、
键盘缓冲 `0x21360E0`、XInput，写进各输入源 `+0x48` / `+0x4C`）→ `0x705715` 进 `System::Update`（渲染 + 步进，步进读的是
**上一帧**写好的动作封装）→ `0x7058C7` 才调 `0x77320`（`add rcx,0x5AE8; jmp 0x7CDC0`，`edx = n`）把输入源写进封装、清边沿再重设。
所以第 j 帧步进读到的是第 j-1 帧采的输入：输入到步进固定多一个 tick（latency-3 要把封装更新挪到 `System::Update` 之前）。第三方实测「主循环与 Present 超过 60，
但不同的镜头矩阵每秒只有约 60 个」（§3）与此一致。

## 2. 耦合点：n = 0 的帧会怎样

### 2.1 按 tick 走、不受影响的（H）

| 子系统 | 位置 | 说明 |
|---|---|---|
| 全部对象更新、物理、AI、武器、弹 | `0x1198FD0..0x119972E` | 按 n 循环 |
| 视口镜头步进 | `0x11995A6 → 0x118DF40` | 在 tick 循环内（暂停时 `0x119953B` 起另走一遍，也只在跑 `System::Update` 的帧） |
| 游戏时间 `System+0xCE4` | `0x1198E0A` | += n/60；n = 0 时不动，着色器时间发同一个值（画面上就是 60 Hz 的阶梯，见 §2.3） |
| 动作重复倒数 | `0x1182C22: sub [rcx+8],r10d`（r10d = n） | 按 tick 减，重复速率不受帧率影响 |
| 本插件的逻辑 | `crew.cpp SharedFrameTick` 等 | 以 `GameFrame()`（场景步进计数 `+0xCE0`，tick 循环内 `0x1198FD0`）去重，由对象更新驱动，不会多跑 |

### 2.2 每帧都跑、n = 0 帧会多跑的（H，`Application::Update` `0x705530`）

| 位置 | 是什么 | n = 0 帧的后果 | 处理（阶段 2） |
|---|---|---|---|
| `0x705633..0x7056AE` | `SteamAPI_RunCallbacks`、前台状态 → `EOS_Platform_SetApplicationStatus`、`0x788460`（全局 `[0x20B2AC8]` 的 Update，第三方称 net::Network::Update，名未核实）、`0x12ADB30`（内调 `EOS_Platform_Tick`） | 调用频率随帧率涨；联机层（含 EDF6Coop 的钩子）的节奏变了 | 只在 n ≥ 1 的帧跑整块（跳到 `0x7056B3`），保持原节奏 |
| `0x7056BA` | `0x1230A0(MapMgr)`：`0x12341F` 处 `MapMgr+0xCC += MapMgr+0xC8`（`0x1233FC` 的 `0x1195E70` 为真时整段跳过；`+0xCC` 超过 `0x176A3BC` 的 ≈1.7e38 时先置为 `0x176A3C0` 的 ≈-1.7e38 再加），`+0xC8` 在 `0x121555` 初始化为 `0x3C4CCCCD`（0.0125）。`0x1230A0` 另一个直接调用者是 `0x9D773`（函数 `0x9D700`，唯一调用者 `0x9D50F`，看上去是场景建立时的一次性调用，未逐层核实，M） | 植被风时间按帧加：帧率翻倍风就快一倍 | 只在 n ≥ 1 的帧调；画面上的风用 `+0xCC + 0xC8 * 相位` 插值（阶段 5） |
| `0x705963` | `Application+0x6C`（输入抑制倒数）`> 0` 时每帧 `dec` | 抑制时间随帧率缩短 | n = 0 帧不减（`[r14+4]` 就是 n） |
| `0x7058C7 → 0x77320 → 0x7CDC0` | 输入管理器每帧更新，逐个动作调 `0x1182BC0`（全 EDF.dll 154 处调用） | 见 §2.4：按键边沿丢失 | 封装更新挪到 `System::Update` 之前、只在 n ≥ 1 帧跑（§2.4 修法） |
| `0x7058F7` `0x119D270`、`0x705946` `0x7B3010`、`0x705957` `0x7AF3E0`（声音）、`0x7059BE` `0x11A1CA0` | 都传 `dt`（`[r14]`） | 按时间推进的，帧率无关（**M**：传参核实了，内部没逐个看；UI 动画是否全按 dt 要实机看） | 无；实机清单 §7 |
| `0x7058B7` `0x11977F0` | HUD / 渲染派发 | 每帧画，正常 | 无 |
| `0x705570` | 全局共享随机数 `[0x1F54128]`（LCG，全 EDF.dll 1191 处引用）每次调用推进一次 | 随机序列随帧率偏移（玩法分布不变，序列与 60 帧不同） | n = 0 帧不推进（34 字节换成调近处叶桩：`cmp [r14+4],0` 为 0 跳过） |
| `0x7B3010` 内 | SoundController `+0x3C` 每次向目标平滑 0.1、`[+0xD8]` 每次 +0.01（同函数里的计时器按 dt） | 音量过渡随帧率变快（只影响声音） | 阶段 2 未处理，实机清单 §7-3 听感对照；要修就把这两处按 dt 缩放 |
| `0x11A1CA0` 内 | xgs::debug 模块计数 `inc [module+0x38]` | 只在调试模块里，正式游戏无影响 | 无 |

### 2.3 渲染侧的「时钟」（n = 0 帧画同一个值 → 仍是 60 Hz 的动画）

| 数据 | 位置 | 级别 | 插值办法 |
|---|---|---|---|
| 玩家镜头世界矩阵 | `CharacterGhostCamera`（vtable `0x1768C10`）`cam+0x220..+0x25F`，步进写、`0x118DFF0` 渲染读（`0x118E0FF` 交 Umbra） | H | 存上一步与这一步，渲染前按相位刚体插值（`InterpolateRigid`），渲染后还原 |
| 着色器时间 | `System+0xCE4` → `0x112BAA0` → XGL 状态 `+0x158`（第三方说法，`+0x158` 未核实） | M | 发 `时间 + 相位/60`，不写回 `+0xCE4` |
| 植被风 | `MapMgr+0xCC` | H | `+0xCC + +0xC8 * 相位`，在读它的渲染点替换（第三方列了 6 处读点，未核实：L） |
| 角色 / 载具骨骼 | CAS 蒙皮（第三方：`0x11009A0` / `0x1100F10`，3 个调用点）| L | 每个模型存两步的骨骼矩阵，渲染时插值；最大的一块 |
| 粒子、拖尾、带状特效、天气、弹 | 各自的更新 / 提交路径 | L | 逐类找位置历史；第三方做到静态，从未实机跑过 |

只插值镜头、不插值角色时，角色（尤其第三人称下镜头跟着的玩家）相对画面会按 tick 抖：镜头每帧都在动，角色只在 tick 帧动。
第三方的用户实测正是「镜头顺了，但跳跃等动作仍像 60 帧，并且有卡顿」（§3）。所以**镜头插值不能单独发布**，至少要和玩家角色、
载具的根变换一起上。

### 2.4 输入（H）

- **按键边沿**：`0x1182BC0`（动作封装更新）每次调用先清 `+0x11` 按下 / `+0x12` 松开 / `+0x13` 重复脉冲，再按「这一帧看到的变化」重设；
  按下时重复倒数 `+8 = 0x10`，之后每次减 n、到 0 置 2 并给脉冲。它每帧都跑（`0x7058C7`，在 `System::Update` 之后、UI 之前）。
  模拟在下一帧的 `System::Update` 里读这些字节。两帧都是 n = 0 时，第一帧设的边沿在第二帧就被清掉，没有任何一步看见：
  **按得快的键（换弹、换枪、跳）会丢**。帧率是 tick 率的两倍以上时经常发生。修法：n = 0 帧在原函数清之前把未被步进读过的边沿
  记下，下一个 n ≥ 1 帧在 `System::Update` 前 OR 回去（`frame_rate_logic.h` `BeforeUpdate` / `ForStep`）；UI 照常每帧从原生字节
  只看到一次。`frame_rate_check` 用随机按键与随机 n 序列验证：有保留时每个含按键的 tick 恰好看到一次，UI 每个按键恰好一次；
  没有保留时步进漏掉大部分。阶段 2 接入时还要核对两点（未核实）：一是在两个步进之间按下又松开的键，步进会同时看到按下与松开、
  而 `+0x10`（当前是否按着）已是 0，原版 60 帧下不会出现这种组合，读按下边沿时又看 `+0x10` 的动作（蓄力、按住）要逐个看；二是
  OR 回原生字节后到下一次封装更新之间，除步进外还有谁读这些字节（`System::Update` 内的 HUD、`0x7058B7` 的渲染派发），不能让 UI
  第二次看到同一个边沿（第三方 R19 的「按一下走两格」）。
- **鼠标位移**：`0x1188479` 调 `0x11831F0(dl=1)`：取出窗口线程累加的 16 字节 `0x1FEEE20` 并清零；`0x1188738` / `0x1188756` 经
  `0x1182A00` 把 X / Y 写到 MouseMoveX / Y 动作源 `+0x48`（每帧覆盖，不累加）；本帧末 `0x7058C7` 的封装更新再把 `+0x48` 拷进
  封装 `+0xC`，下一帧的步进读封装。n = 0 帧的位移在封装里只待一帧，下一帧的封装更新就覆盖掉，模拟看不到：
  **高帧率下视角转动变少、且随帧率变化**。
- **滚轮**：`0x1188480` 调 `0x11832D0(cl=1)` 取走 `[0x21360C0]` 并清零（窗口过程 `0x1183FE3` 累加），同样经封装进步进。
- **修法（2026-11-24 更正，阶段 2 实际做法）**：旧版写的「在取的那一层累加鼠标」「n = 0 帧不取滚轮」「`Shadow` 把边沿 OR 回」都不对或
  不必要：输入要过一帧（`0x7058C7` 的封装更新）才轮到步进，n = 0 帧的封装更新会覆盖上一帧写好的值。阶段 2 改为**把封装更新挪到
  步进之前、只在有 tick 的帧跑**（这同时就是 latency-3：输入少走一帧）：
  - 钩 `0x705715`（`System::Update`）：n ≥ 1 时先调原封装更新 `0x77320(输入管理器, n)` 再步进；n = 0 时不更新封装，只做
    `ClearForUi`：清每个封装的 `+0x11/+0x12/+0x13` 与每名玩家的按下 / 重复 / 松开掩码（`+0xDBC/+0xDC0/+0xDC4`），把源
    `+0x48` 拷进封装 `+0xC`（源 `+0x4D` 关闭的跳过），UI / HUD 这一帧看不到边沿、但看得到当前摇杆 / 位移值。
  - 钩 `0x7058C7`：本帧已在步进前做过就跳过，否则（帧门没开、或 `[rdi+9]` 那条路径没经过钩子）照原版调。
  - 鼠标取（`0x1188479 → 0x11831F0`）与滚轮取（`0x1188480 → 0x11832D0`）：n = 0 帧不取，窗口线程的累加留到下一个有 tick 的帧，
    返回「没动」（鼠标给 `0x1765B30` 的 `{0,0,0,1.0}`，滚轮给 0）。
  - 封装更新的长按重复倒数是减 n（`0x1182BC0`），只在 n ≥ 1 帧调，重复速度与 60 帧一致；按键状态在 tick 帧采样，与原版 60 帧下
    每帧采样一次等价（两个 tick 之间按下又松开的轻点原版也看不到）。
  - `frame_rate_check` 的 `InputEdges` 用这个顺序建模：20 万帧随机按键 / 随机 n，步进看到的按下 = tick 采样到的按下，UI 看到同样多；
    对照（原版顺序、帧率高于 tick 率）步进漏键。`frame_rate_logic.h` 原来的 `Shadow` / `BeforeUpdate` / `ForStep` 已删。
  - 已知残留：原版 `[rdi+9]` 置位那一帧（主循环跳过 tick 计数）不经帧门，`Steps()` 仍按帧门上次的 tick 数判定，可能少取一帧鼠标位移
    （M，实机清单 §7-4 看）。

## 3. 第三方研究包（`D:\APP\edf6-120fps-kit`，不可信数据，只读，不运行、不拷贝）

一个名为 EDF6 Modernization 的 EDFModLoader 插件（`EML6_Load`）的源码、审计记录与运行日志，2026-09 到 11 月。要点：

- **帧门**：把 `0x11A2F4F` / `0x11A2F6B` 的 `call 0x11DAE60` 换成自己的判定（返回 eax = 本帧是否出帧、edx = tick 数），
  两处 `mov ebx,eax` 改成 `mov ebx,edx`；出帧节奏借游戏里一个现成的可配置帧计时器（`[0x2139B90]+0x18`，设置函数 `0x963DF0`
  写 `+8` = fps、`+0x18` = 1/fps，判定函数 `0x963E10`）。设置函数唯一的调用者在 `0xA0041`（H：反汇编核实了这两个函数的内容与调用者；
  `0x963E10` 没有直接调用者）。
- **节奏守卫**：网络块、滚轮、`+0x6C` 倒数、MapMgr 只在 n ≥ 1 的帧跑（与 §2.2 结论一致，我方已独立核实）。
- **输入**：R19 曾让边沿在 n = 0 帧保留，结果 UI 在两帧各看到一次（菜单「按一下走两格」）；R20 改成 n = 0 帧照常清给 UI、另存一份
  给下一步（与 §2.4 的保留方案同构）。R32 修正鼠标位移的累加与发布顺序。
- **镜头**：R33 在渲染准备 `0x1197B50 → 0x118DFF0` 处，对 `CharacterGhostCamera` 的 `+0x220` 用上一步 / 这一步插值、渲染后还原，
  以 `+0x52C`（第三方称步进代数，**未核实**）判断是否新的一步。注意：本插件的瞄准镜画中画早已把 `0x1197B50` 这个调用点
  改指向 `scope_lens.cpp` 的 `ProjectHook`（`RedirectCall` 会核对原目标，第二次挂必然失败），镜头插值只能并进 `ProjectHook`，
  或先把它重构成共享派发（阶段 3）。实机遥测（RTX 3060 笔记本，离线）：模拟 59.92 Hz、Present 约
  90 Hz、运动中每秒约 90 个不同的镜头矩阵。**用户反馈：镜头顺了，但仍有卡顿，跳跃等动作仍像 60 帧。**
- **其余域**：角色骨骼（A2）、植被（F1）、着色器时间（X1）、粒子 / 拖尾 / 带状 / 天气 / 弹（V1R-D1-U1）都只到「静态检查通过」或
  「链接产物审计通过」，**没有一个跑过实机**。其文档自己写明「完整的 120 帧视觉 / 游戏未建立」。
- **被否决的**：跳过 Umbra `resolveVisibility`（加载卡死）、Umbra 重发缓存（无收益）、辅助可见性降频（黑闪、阴影成块更新）。
- **性能**：n = 0 帧并不便宜。其分析里图形工作线程栅栏约 7 ms、Umbra `processVisibility` 每帧约 3 次、每次约 3 ms；某次测得
  n = 0 帧约 9.1 ms、n ≥ 1 帧约 5.5 ms（L，单机单场景）。也就是说在中端机上，解耦后实际能到的帧率大概在 90 上下，
  「不限帧率」的上限由每帧渲染成本决定。

我方没有拷贝它的任何代码或二进制；地址都按上面的级别自己核实过才写进本文。

## 4. 方案

### 4.1 帧门（阶段 2）

- 把 `0x11A2F4F` / `0x11A2F6B` 两处 `call 0x11DAE60` 指向一个近处小桩：`sub rsp,28h; call 判定; mov rdx,rax; shr rdx,32; add rsp,28h; ret`，
  两处 `mov ebx,eax`（`8B D8`）改成 `mov ebx,edx`（`8B DA`）。判定返回低 32 位 = 出不出帧、高 32 位 = tick 数。小桩在
  `AllocateNearCode` 的页里，用 `RtlAddFunctionTable` 登记 unwind（`UWOP_ALLOC_SMALL 0x28`），异常回溯能穿过它。
- 判定（`frame_rate_logic.h`）：先看呈现槽（`Ready`），没到就返回「不出帧」——**不调** `0x11DAE60`，因为它一数就把 `last`
  往前推，数了不出帧那几个 tick 就丢了；到了才调原 `0x11DAE60` 拿 n（可以是 0）。所以 tick 照原版边沿对齐，模拟长期保持
  59.94 Hz；步进最多被推迟一个槽（`frame_rate_check` 在 61 / 120 / 144 / 240 / 1000 / 不限下各跑 30 s 假时钟：每个过去的 tick
  恰好步进一次，显示时间单调、不跳）。
- 等待：循环里的 `Sleep(1)` 已是 `TickWait`；开启后改为等到下一个槽（`WaitCounts`），不再等 tick 边界。`FrameRateCap=-1` 不等。
- 垂直同步（H，见 §1）：SyncInterval 由 `0x11A3098` 的 `sete dl` 决定，平时恒为 1、追帧后 8 个渲染帧为 0，游戏里没有设置项。
  帧门开着时由插件接管：钩 `0x11A309B`（目标 `0x111D890`）自己算 dl：`FrameRateCap = 0` 照原版；开着时追帧窗口改按 tick 计
  （8 个 tick），上限高于刷新率或不限时传 0。开着 SyncInterval = 1 时帧率上限是显示器刷新率；60 Hz 显示器开垂直同步就没有意义。
- 排队帧数：开 `FrameRateCap` 时必须同时把 DXGI 最大排队帧数设为 1（`MaxFrameLatency`，`frame-pacing-re.md`），否则产帧率一高于
  刷新率，SyncInterval = 1 加默认 3 帧的队列会让 Present 一直堵在队列满的状态，延迟多 2–3 个刷新周期，正好抵消高帧率想要的低延迟。
  交换链是旧的 blt 模型（DISCARD、BufferCount = 1，`0x111B4C0..0x111B53A`），真正上屏不卡在刷新率还要翻转模型 + ALLOW_TEARING（latency-5）。

#### 4.1.1 加载期间不开帧门

加载画面上多出的 0-tick 帧只是把加载画面重画一遍，没有可插值的东西，还要占 CPU / GPU，拖慢加载。所以加载期间帧门按原版节奏走：
先数 tick，有 tick 才出帧，没有就等到下一个 tick 边界（`pacing::CountsToBoundary`，与 `FrameRateCap = 0` 时 `TickWait` 等的一样），
每个出的帧都步进；槽保持未上膛，加载结束后第一帧从当时重新起槽，不会为加载那段时间补发一串帧（`LoadingRuns`）。

判据：游戏自己的加载计数 `0x2139AB0 + 0x34` 大于 0（H，静态，EDF.dll 0x678CCB46，`frame_rate_sig_audit` 逐条核对）。

- 写：`0x1133FC0(obj, dl)` = `movzx eax,dl; lea eax,[rax*2-1]; lock xadd [rcx+34h],eax; ret`，dl = 1 加 1、dl = 0 减 1。
  15 个调用点全是这个计数：13 个直接传 `lea rcx,[0x2139AB0]`；另 2 个（`0x110B460` 里成对的 `0x110B527` / `0x110B644`）
  传 `mov rcx,[0x2135930]`，而 `[0x2135930]` 唯一的写入点 `0x10FFE3C` 写的是参数 2（`0x10FFC7A` `mov rbx,rdx`），唯一调用方
  `0x700F12` 传 `lea rdx,[0x2139AB0]`——也是 `&0x2139AB0`：
  - +1：AS `BeginLoading`（`0x1ACB10`）的 `0x1ACC03`、BVM native 0x0A `0x21070F`、`0x20FC24`、启动 `0x9E014`、
    `UiHQ_3DModelView` 异步回调 `0x9424C4` / `0x942542` / `0x9425B4`；
  - -1：AS `EndLoading`（`0x1B49D0`）的 `0x1B4A69`、BVM native 0x0B `0x210889`、`0x21FBD6`、上面三个回调里成对的
    `0x9424DF` / `0x94255B` / `0x9425CF`。
- 清零：`0x1133400` = `mov dword [rcx+34h],0; ret`，9 个调用点（7 个 `call`、2 个尾跳转 `jmp`）全是 `0x2139AB0`：`BeginLoading` 自己在 +1 之前（`0x1ACBF5`）、
  场景拆除 `0x70FEBA`、BVM native 8 `0x2105AF`、按名加载脚本 `0xB1A4F`、加载 `MainScript.as` 的 `0xB7C29`、`0xA1AF5`、启动 `0x9DF99`，
  以及尾跳转 `0x1B997D`（前面 `0x1B9971` `lea rcx,[0x2139AB0]`）、`0x226990`（前面 `0x226949`）。
  所以任务加载期间计数正好是 1；`EndLoading` 之后回到 0。
- 游戏自己就把它当「正在加载」：作业线程 `0x1133950` 在 `0x1133993` `lock xadd [rbp+34h],r15d`（读），大于 0 时 `Sleep(16)`
  （`0x1133C02`），不处理 `+0x90` 的作业队列。要是计数平时不回 0，这条队列就永远不跑，所以菜单和任务中它应为 0。
- 549 个任务脚本每个都恰好一次 `BeginLoading`、一次 `EndLoading`（M001：`BeginLoading → Preload… → WaitPreload →
  (Online_WaitStart) → EndLoading`），联机等人进场（`Online_WaitStart`）也算在加载里。
- 判据用 `> 0`，不用 `!= 0`：`BeginLoading` 在 `0x1ACB4E` 的虚调用返回非 0 时跳过清零和 +1，而 `EndLoading` 无条件 -1，
  计数可以短暂为 -1；下一次 `BeginLoading` 会清零。这种情况下那次加载帧门照开（与改动前一样）。
- 没选的：`System+0x68` 场景为空（`0x1198ECA`）的路径根本不渲染，任务加载画面期间场景很可能不为空，盖不住；任务对象
  `+0x2B8`（`BeginLoading` 写 1、`EndLoading` 写 2）没有现成的全局指针；`sync_load_probe` 只在调试版里装。

未经实机确认（静态推断）：启动那次 +1（`0x9E014`）由之后加载 `MainScript.as` 的清零抵消、菜单里计数为 0；`UiHQ_3DModelView`
的成对 +1 / -1 会让菜单里看 3D 模型时短暂关掉帧门。日志每次加载开始写 `FRAMERATE loading (count N)`、结束写
`FRAMERATE loaded after X s, N frames`，每 5 s 的 FRAMERATE 行带 `% of the frames loading`，实机看这几行即可确认。
签名（`0x1133FC0` 的 16 字节、`0x1133993` 的读）不符时帧门整套不装（与其它点位一样全有或全无）。

### 4.2 节奏守卫（阶段 2，§2.2 / §2.4）

网络块（逐个调用：`0x705633` / `0x705693` / `0x7056AE` / `0x7056BA`）、`+0x6C` 倒数（叶桩读 `[r14+4]`）、共享随机数 `0x705570`
只在 n ≥ 1 帧跑；阶段 3 再加两个（#371 审查第 3 条，dt 逐个核对后）：音量平滑 `0x7B3010`（`0x705946` 调用，
`+0x3C` 每次逼近 0.1、`+0xD8` 每次涨 0.01，按调用次数走）只在 tick 帧调，参数传上次调用以来各帧 dt 之和；负载计
`0x2139B84`（`0x11A3033` 写，LOD 裁剪 `0x134210` / `0x136621` 按 200–350 % 阈值读）只在 tick 帧写，0 tick 帧的轻 Update
不把它拉低。共 8 个守卫，缺一个就不装帧门。所有守卫都读最终 n（`0x11A2FD8` 把 ebx 存进 `[rsp+0xBC]` 之后，
即 `[rdi+9]` 置 0 和夹取之后的值），与 `[r14+4]` 一致。

逐个核对过、不需要守卫的（0 tick 帧带真实 dt 也不出错）：`0x705597` 的 `+0x68` 累加（全 EDF.dll 无读者）；
`0x7AF3E0`（按时间，不按次数）；`0x11A1CA0`（只在调试开关下跑）；`0x119D270`（只建 UI 的 UpdateContext，`+0x10` 放 dt，本身不累加；用它的各 UI 类见下面「未核实」）；`+0x6C` 守卫顺带跳过的 `0x70596F` → `0x77200`（停震动、重新枚举输入设备，
`+0x6C` 由 `0x704E60` 置 8，倒数只在 tick 帧走，原版也是 8 tick 后调一次，跳过 0 tick 帧是对的）。
未核实：几个 UI 类 OnUpdate 里按调用次数自增的字段（HUiMissionResult+0x794、HUiLobby+0x9DC、HUiRoom+0x8B4、
HUiRoomFixedPhrase+0x8F4、HUiRoomSetting+0x7EC、HUiOpening+0x10、UiNotice+0x28），读者未查，可能让这些界面的
动画在高帧率下变快，列为 §7 人测项。输入见 §2.4 修法（封装更新挪到步进前，也就是 latency-3）。阶段 2 结束时画面仍是 60 Hz 的重复帧，
但可以实机验收「模拟节奏、输入、联机不受影响」这一层，然后再加插值。

### 4.3 插值（阶段 3 起）

相位 `RenderAlpha`：n ≥ 1 的帧为 1（渲染在步进之前，画的就是这一步），n = 0 的帧为距上个边界的 tick 比例。每个域存「上一步 /
这一步」，在渲染读它的那一刻换成插值值、渲染后还原（不写回模拟状态）。遇到断点（瞬移、切镜头、换地图、载入）不插值：
`InterpolateRigid` 对超过 `maxMove` 米 / `maxTurn` 弧度、非刚体、手性不同、NaN 一律拒绝，调用方照原样渲染。

- 阶段 3：玩家镜头 + 玩家角色 / 所乘载具的根变换（两者必须同时上，见 §2.3）。镜头插值的挂点 `0x1197B50` 已被 `scope_lens.cpp`
  占用（§3），要并进它的 `ProjectHook`。插件自己改 `cam+0x220` 的功能（地图俯视 `map.cpp`、
  第一人称 `firstperson.cpp`、敌控镜头、遥控武器站视角、炮塔镜头）都在步进里写，渲染前插值覆盖的是它们写完的结果，正常；但
  它们切换时是断点，要靠 `InterpolateRigid` 的拒绝或显式「本步是切换」标记，阶段 3 逐个核对。
#### 4.3.1 镜头（fps-5 / fps-6 / fps-8，`src/frame_rate_view.cpp`）

- 快照（fps-5）：tick 循环里每个视口的镜头步进 `0x118DF40` 只在 `0x11995A6` 调用（`rcx` = 镜头，`rdx = lea [rsp+38h]`），它是循环的
  最后一个调用，排在各对象阶段（vtable `+0x38/+0x30/+0x20/+0x40/+0x28/+0x48`）之后。H。插件的镜头功能都挂在镜头 vtable 槽 4 上，
  步进返回时都已写完。钩子按镜头记 `prev / cur`（`cam+0x220` 64 字节世界矩阵 + `cam+0x24` 视野），最多 8 台；追帧（n = 2、3）时
  prev 是倒数第二步。
- 投影（fps-6）：`scope_lens.cpp` 的 `ProjectHook`（`0x1197B50 → 0x118DFF0`）开头调 `SetBeforeProject` 注册的回调。n = 0 帧
  在投影前把 `cam+0x220` 写成 `InterpolateRigid(prev, cur, alpha)`、视野线性插值。字节已不等于 cur（别处在步进后改过）就不动。
  本帧帧末栅栏 `0x11A305A → 0x111CC20`（渲染线程已画完）后仍等于写入值的还原成 cur（`BeginFrame` 开头再兜底一次），所以下一帧的
  `Application::Update`、步进和插件逻辑读到的永远是模拟值。
- 断点（fps-8）：`FrameRateCameraCut(camera)`（`nullptr` = 全部）把这对 prev 设成 cur，下一步不插值。已接入的调用点：地图俯视
  开关失败与异常强退（`map.cpp`）、第一人称开 / 关（`firstperson.cpp`）、敌控镜头接管与交还（`firstperson.cpp` `enemyViewLast`）、
  瞄具缩放按下与复位（`sightzoom.cpp`）、步兵瞄具缩放档变化（`infantryscope.cpp`）、炮塔镜头三处硬复位（`turretcam.cpp`）。
  `InterpolateRigid` 自己拒绝一 tick 内超过 10 m / 1 rad 的跳变。

#### 4.3.2 玩家根变换（fps-7）

- 采样：在镜头步进钩子里（tick 结果已定），`h = [cam+0x360]`（vtable 是四个兵种之一才算），徒步取身体实例 `[h+0x900]` 的 pose[0]，
  骑乘（`HumanOnFoot` 为假）取载具实例 `v+0xEE0`（`v = [h+0x1548]`）的 pose[0]。每 tick 一次，只由第一台跟着这个兵的镜头采样。
  身份（h、v 及其控制块 `+kSelfCtrl`、实例指针）变了就清零重来。
- 写点：n = 0 帧在 `System::Update` 里的渲染录制调用 `0x1198FA4 → 0x11978D0`（`System_RecordDraw`）之前，由 `RecordDrawHook`
  写；`BeginFrame`（`System::Update` 之前）只设 alpha / ticks / age，不写。依据（H，汇编核对）：
  - `System::Update` `0x1198DA0` 进录制前依次调 `0x1195A80`、`0x1195F20`（整理对象表，会删对象、摘掉更新表里的裸指针）、
    `0x1197680`，再过 `0x1198F84 / 0x1198F8D` 两道门才到 `0x1198FA4`。在 `BeginFrame` 写，`0x1195F20` 删掉的对象就带着写过的
    pose 进了还原表；在录制调用处写，对象表已是本帧最终状态。
  - 调用点字节（`0x1198F96` 起）：`41 B0 01`（`mov r8b,1`）、`41 0F B6 96 E9 0C 00 00`（`movzx edx,byte [r14+0xCE9]`）、
    `49 8B CE`（`mov rcx,r14`）、`E8 27 E9 FF FF`（`call 0x11978D0`）；安装前整段比对（`kRecordSig`），`0x1198FA9` 不用 `rax`。
    `0x11978D0` 另有 4 个调用点 `0x93C3F / 0x9D8BA / 0x9DE91 / 0xBB48B`（载入 / 菜单画面），不挂。`frame_rate_sig_audit.py`
    对真 `EDF.dll` 核对签名、恰好这 5 个直接调用者、`0x1195F20` 在录制之前。
  - n = 0 时 `0x1198FB3 je 0x1199734` 跳过整个 tick 循环（`0x1198FA9..0x1198FB3` 只存 `[rsp+0x30]`、判 n）；循环后的 `0x1199753 → 0x11BE100`（清队列）、
    `0x1199764 → 0x118EFD0`（Havok 内存）不读绘制 pose。渲染线程在执行绘制命令时（`0x11009CB`）才读 `[inst+0x30]`，
    所以还原仍要放在帧末栅栏之后，不能放在录制返回后。
  - 一帧只写一次（`poseDue` 在写后清零，栅栏也清零：录制没来的帧不会拖到下一帧写）。
  `D = cur⁻¹ · InterpolateRigid(prev, cur, alpha)`，
  右乘到下列模型**每个实例**（`model+0xA0`、基础 LOD `[model+0x1B8]`、LOD 表 `[model+0x250]` 各项 `+0x58`）**每根骨**的 pose
  （`[inst+0x30]`，个数 `[inst+0x20]`，每骨 0x40 字节世界矩阵）：身体 `h+0x860`、`[h+0x1950]` 全部武器的 `+0xF30`、骑乘时的载具
  `v+0xE40`。骑乘时身体和武器也乘载具的 D（刚性乘客）。蒙皮按每根骨自己的矩阵算，只改根骨会把皮撕开，所以全部骨骼都要乘。
- 还原：本帧帧末栅栏后（`BeginFrame` 开头兜底），实例 / pose 指针 / 个数没变的，**逐骨**比对：仍等于写入值的骨还原成写入前，
  别人写过的骨归别人。记录和前后两份拷贝在第一次写之前就入表，写到一半出异常也能还原。
- 第一人称视图模型的锚点取自绘制时的 pose，D 在 `anchor⁻¹` 里抵消，徒步不会乘两次。骑乘第一人称走镜头步进时算的 stepT
  （`firstperson.cpp` DrawTransforms 失败分支），不跟插值后的镜头，是已知缺口。
- 没覆盖：n ≥ 1 帧的原版竞争（渲染线程可能读到本帧步进正在写的 pose，60 帧下每帧都同样
  落后所以看不出；根治要挂 `0x1100F10` 写暂存区，阶段 4 一起做）。
- 日志：每 5 s 的 `FRAMERATE` 行带 `0-tick projections blended / as stepped` 和 `player root blended / as stepped`。

#### 4.3.3 其余对象的根变换（阶段 4 PR-e，`src/frame_rate_objects.cpp`）

逆向（H，汇编核对）：

- `System = [image+0x20B2958]`（`scene::ObjectManager`）。`+0x448` / `+0x458` 是每 tick 要更新的对象表（裸指针数组 / 个数）。
  `0x1198DA0` 的对象阶段逐个调用它们；有父对象（`[obj+0x38]≠0`）的也在表里，只是跳过。`+0xCE0` 是 tick 计数，每 tick 在
  `0x1198FD0` 加 1（`[sys+0x68]==0` 时走 `0x1198EE0`）。
- 一个 tick 里的调用顺序：
  1. `0x11993D6` 调 `0x1195F20` 整理对象表。
  2. 对象阶段。
  3. `0x119950B` 调各管理器的 slot 0x48。
  4. `0x11995A6` 镜头步进（采样点）。
  5. `0x11996B3` 调 `0x1193D50`，即各管理器的 slot 0x28。
- `0x1195F20` 整理对象表的过程：
  1. 先走 `+0x4A8`，删掉 `+0x18` 带 4 位的对象（`0x118A1B0`）。
  2. 再走 `+0x3E0` 链表。节点 `[2]` 是对象，`[3]/[4]` 是 weak_ptr。
  3. weak_ptr 已失效的，从 `+0x420/+0x440/+0x460/+0x480` 各表摘掉裸指针。
  4. 其余的按 `+0x19` 对 `+0x1A` 同步各表成员（bit4 → `+0x448`）。
- 所以**表里的裸指针在两次整理之间可能已经悬空**，不能在 0-tick 帧凭表判断对象还在不在。
- 对象自身的弱引用：`+0x28` 存 self，`+0x30` 存控制块。控制块 `+8` 是 use 计数、`+0xC` 是 weak 计数，vtable 为 {destroy, delete}。

做法：

- **采样**：在镜头步进钩子里，每 tick 一次（按 `+0xCE0` 去重，多视口、追帧 n = 2/3 每 tick 各采一次）。
  - 遍历更新表，只取 `thermal_models.cpp` 认得的家族：人形 / 士兵 / NPC / 他机玩家（HumanBase）、载具（含空车，VehicleBase）、
    虫、巨人、怪兽、UFO 等。`+0x18` 带 4 位（待删）的不采。
  - 采每个对象主模型实例 `model+0xA0` 的 pose[0]。
  - 新对象在它的控制块上加一个 weak 计数，以后判活只看 use 计数，不读已释放内存。某 tick 不在表里了，就归还 weak 并删记录；
    任务场景释放时（`mission.cpp` 的 `ReleaseGroupHook`，组 2，与 `crew::SceneOver` 同处）`frameobjects::SceneOver`
    先还原、再归还全部 weak、清空记录。
  - 身份（控制块、vtable、实例）变了，或上一 tick 没采到，就重新计数。
  - 表只在 tick 帧扩容（初始 1024 对象、4096 个 pose、1M float），扩容在 `noexcept` 里 `try/catch(std::bad_alloc)`：
    失败则本 tick 不采样（之后的帧照 tick 画），不抛出。`Install` 的初始预留同样，失败就不启用本层，记一行日志。
- **为什么采样留在镜头步进，不挪到 tick 末尾**：镜头步进是 tick 里最后一个每 tick 都跑的直接调用。它之后依次是
  `0x11BEBE0`（Havok 查询回调）、`+0x358` 作业表（各元素 vtbl[1]，经 `0x118FC00`）、不暂停时 `0x1193D50`（`[sys+0xCC0]` 各项
  slot 0x28，再 `+0x370` 作业）、再一次 `+0x358`。这些都是运行时按 vtable 选的调用，静态无法确定哪个会写模型 pose，也就找不到
  一个「保证看到所有写入」的更晚的点。代价：之后被写过根的对象在 0-tick 帧发现绘制的 pose[0] ≠ cur，照 tick 画并计入
  `pose` 原因，不会用过期的一对插值。实机若 `pose` 计数高，再按日志找写入者。
- **读法（性能）**：采样和写入读的都是游戏此刻持有的活对象（镜头步进时在更新表里的；自己控制块 use 计数 > 0 的；座位 /
  武器架 weak_ptr 活着的），不再逐个问 `Readable`，整段在 `__try` 里。`thermal_models` 为此加了 `EnemyModelsLive` /
  `EnemyModelLive` / `EnemyFamilyLive`：同样的 RTTI 规则和缓存，只有第一次见到的 vtable 才经 `Readable` 解析 RTTI，模型 vtable 的
  判定也按 vtable 缓存。`Readable` 只问 System 和它的更新表：离线测试 `frame_rate_objects_test` 中 20 个和 2000 个对象的采样都只问
  2 次、一帧写入也只问 2 次（审查时 stress:30 采样每步 4.74 ms 全在 `Readable`）。例外：载具扳机武器的登记检查
  `IsAnimationModel` 走带检查的读法，每把武器每帧问一次（只有载具才有，数量少）。
- **写**：n = 0 帧，在 fps-7 之后，同在渲染录制调用 `0x1198FA4` 的钩子里（见 §4.3.2 写点）。
  - 对象必须还在、vtable 不变、当前绘制的 pose[0] 仍等于 cur（tick 后没人改过）。
  - `D = cur⁻¹ · InterpolateScaled(prev, cur, alpha)`：均匀缩放按比例插值；挤压 / 镜像 / 一 tick 超过 `kCutMove` 10 m 或
    `kCutTurn` 1 rad（57°）的不插值。这两个阈值不是游戏里读出来的：是 fps-8 给玩家根定的「瞬移 / 复活 / 镜头切换」判据
    （`frame_rate_view.cpp`），这里沿用，让对象和玩家根判法一致。真实运动若超过它们，会照 tick 画并计入 refused 的
    move / turn，实机看这两个计数决定要不要按家族调整。
  - 右乘到对象 `EnemyModels` 给出的每个模型、每个实例、每根骨上。四个兵种类（含 NPC）连带 `[h+0x1950]` 的武器一起乘。
  - **载具扳机武器**：载具 `+0x638` 武器架（`+0x648` 个数，步长 0x48，`+8` 控制块、`+0x10` 武器），控制块 use > 0 且武器
    `+0xF30` 是已登记的 AnimationModel（`thermal::IsAnimationModel`：vtable 是 EDF.dll 的或 RTTI 是 AnimationModel，且 `+0x10`
    Umbra 对象已设）时，乘这辆车的 D；不是的不碰。注意：载具武器 `+0xF30` 是否真的作为独立模型绘制，静态没有确认；
    登记检查只保证不写非模型内存。
  - **乘员随车**：先走每辆载具（`+0x608` 座位，按座位 weak_ptr 判活）。座位上的人形（同车 NPC、EDF6AutoTurret 副炮射手、
    他机玩家）及其武器一律乘这辆车的 D，不用自己的。玩家载具的其他乘员乘 fps-7 的 D。车停着，乘员算「静止」；车不插值，乘员也
    照 tick 画，原因随车。
  - **子对象**（`[obj+0x38]` 有父对象）：在更新表里的，和其它对象一样用**自己的** D，不跟父对象的 D；不在表里的照 tick 画。
    刚性连着的父子各自插值，结果近似一致，但不保证严格贴合。
  - 玩家本人和玩家载具留给 fps-7，不重复乘。
  - 每个 pose 一帧只写一次（按 pose 指针去重）。先把记录、写前副本和写后副本存好，再写 pose：中途出错也能还原。0-tick 帧不分配；
    表不够时其余对象照 tick 画（`full`），下个 tick 扩容。
- **还原**：与 fps-7 一起放在 `RestoreFrame`（本帧帧末栅栏后），先还原本模块，再还原 fps-7。前提全部满足才还原：
  - 记录仍是同一个对象且对象还在（use 计数、weak-this 控制块不变、未带待删位）。
  - 乘员仍坐在原座位，控制块不变。
  - 模型仍属于这个对象：自己的模型重新取 `EnemyModelsLive`；士兵武器按槽位仍是同一把；载具武器按架位仍是同一把且控制块不变。
  - 实例仍是这个模型的，pose 指针和骨数不变。
  - 然后**逐根骨**比较：仍等于写入值的骨还原，写入后被别人改过的骨保留别人的。
- **联机**：只改画面上的 pose，n ≥ 1 帧不碰，不发包（`frame_rate_net_guard.py` 把本文件列入每帧文件）。
- **日志**：每 5 s 在 `FRAMERATE` 行后另起一行，有数才打：
  - `objects N: blended / (riders) / still / as stepped (gone/vtable/pose/samples/unsampled/refused/full/fault) / most poses a frame`。
    原因：`gone` 对象已释放或待删；`vtable` 地址上换了类；`pose` 采样后根被别处写过；`samples` 只见过一个 tick；`unsampled` 有
    tick 没经过镜头步进采样；`refused` 插值被拒（下面的拒绝计数分原因）；`full` 表不够；`fault` 读出错。乘员随车计原因。
  - 玩家根和对象的拒绝原因计数，分 alpha / not rigid（含 RigidSign 容差）/ mirrored / move / turn。

仍按 60 Hz 画的：

- 挂在载具 / 角色上的特效、粒子、拖尾、光源、弹（不是带骨骼模型的对象，阶段 5）。
- `+0xF30` 不是已登记 AnimationModel 的载具扳机武器。
- `thermal_models.cpp` 规则外的对象类；不在 `+0x448` 更新表里的对象（含不在表里的子对象）。
- 一 tick 内被镜头步进之后的作业改过根的对象（见上「为什么采样留在镜头步进」），计入 `pose`。
- 根有非均匀缩放的。
- 超过 256 种 vtable 后，没进缓存的类每次都现查（只影响性能，不影响结果）。
- n ≥ 1 帧的原版竞争（同 fps-7）。

- 阶段 4：所有角色 / 载具 / 敌人的骨骼。
- 阶段 5：植被风、着色器时间、粒子 / 拖尾 / 弹。

### 4.4 联机

只改呈现，模拟与网络节奏不变（§4.2 让网络块保持原节奏），所以**不需要升房间协议**：同一房间里有人开、有人不开，模拟结果一样。
阶段 2 实机要验证这一点（EDF6Coop 自己的每帧钩子在不在 n = 0 帧多跑，见 Coop 仓库）。

插件自己的联机通道（2026-11-24 审查，`tests/frame_rate_net_guard.py`）：n = 0 帧不跑泵、不发包。泵 `RunSupportNetTick`
（`support_net.cpp`）按 `GameFrame()` 去重，`GameFrame()` 只在 `SeeFrame` 读到 System+0xCE0 变了才推进；+0xCE0 只在
`0x1198EEA` / `0x1198FDA` 写，后者在 tick 循环里，n = 0 时 `0x1198FB3` 跳过整个循环。`SeeFrame` 只在 tick 内调用（载具输入、
NPC Think、空母激光、支援分派、PvP）。直接发包的点都在 tick 路径上或是一次性事件，周期重发按时间或逻辑帧限频。每个渲染帧都跑的
文件（HUD、Present、UI、窗口消息、fps-9 的几处、`map.cpp` 每帧钩子）不发包。低风险：`room_ui.cpp` 每帧调 `RoomPvpTick` 写
EDF6Coop 大厅属性，值不变就跳过，被拒时按调用次数重试（高帧率下重试更频，不分歧）。EDF6Coop 自己的每帧工作挂在
`0x7056AE`，由守卫限在 tick 帧；双机实测留给维护者（§7-5）。

## 6. 离线检查（阶段 1）

`cmake --build build --target frame_rate_check && build\frame_rate_check.exe`（已加入 `offline_checks` 与 ctest）：

- `FixCap`：0 关、-1 不限、1..60 当关、< -1 当关、> 1000 夹到 1000；`PresentPeriod` 向上取整，帧率永不超上限。
- 呈现槽：随机帧耗时下从不在槽前出帧、20 s 平均不超上限；廉价帧恰好在上限；长帧之后下一帧立即出、再下一帧隔一整个周期
  （不补发）；略晚的帧保持相位不漂移；QPC 64 位回绕。
- 整个循环在假时钟上 30 s：tick 只在出帧时数，实际步进数（经 `min(n, 3)` 之后）= 过去的 tick 数，模拟 59.94 Hz；对照：先数 tick
  再看槽、不出帧就丢掉的顺序会少步进（`LoopCountFirst`）；显示时间（步数 - 1 + 相位）单调不退，
  且一次前进不超过一个 tick 加一个槽。
- 渲染相位：步进帧为 1、边界上为 0、过了 tick 未数时夹到 1、QPC 回绕。
- 刚体插值：2000 个随机旋转（含镜像）的四元数往返；端点精确；1/4 处的偏航与位移；镜像保持镜像；跨 ±π 走短弧；瞬移、大转角、
  手性不同、缩放、NaN、相位越界一律拒绝；第 4 列取当前。
- 加载（§4.1.1，`LoadingLoop`）：61 / 144 / 1000 / 不限下 25 s 假时钟、5–15 s 为加载：加载期间没有 0-tick 帧、每帧都步进、
  10 s 出 595–601 帧（约一 tick 一帧）、没 tick 时等到边界；整段每个 tick 恰好步进一次；加载后 0-tick 帧恢复，头 100 ms 不超过
  上限的 1/10 + 2 帧（不补发）；计数 ≤ 0 不算加载。
- 输入顺序：20 万帧随机按键 / 随机 n：封装更新挪到步进前、只在 tick 帧跑时，步进看到 tick 采样到的每个按下恰好一次、UI 同样多；
  原版顺序在帧率高于 tick 率时步进漏键（对照）。

## 7. 实机验证清单（阶段 2 起，逐项 A/B，`FrameRateCap=0` 对照）

2. 帧门：日志统计每 5 s 的 tick 率（应 59.9 左右）与出帧率（应接近上限或显示器刷新率）；垂直同步开 / 关各一次；菜单、载入、

4. 输入：快按换弹 / 换枪 / 跳 / 翻滚 100 次不丢；鼠标同样移动量转过的角度与 60 帧一致（固定 DPI 下来回甩）；滚轮切换武器每格一次。

6. 镜头插值（阶段 3）：快速转视角、奔跑、载具高速、地图开关、第一人称开关、敌控 / 炮塔镜头切换时无跳变、无黑闪；
